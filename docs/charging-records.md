# 課金レコードの要件と設計（下書き）

- 作成日: 2026-10-25
- 状態: 下書き。§3 の決定事項は 2026-10-25 にユーザーと合意したもの（§14 の確認事項もすべて合意し、決定事項 14〜21 にした）。決定事項 22〜26 は 2026-10-30 に aka-ossbss の段階 3-4 の確認事項で合意し、本文を改めた。作りは aka-ossbss の設計概要 §19.2「段階 3-4 で決めたこと」。
- 位置づけ: テナントへの請求の料金を外部のシステムが計算するための記録（課金レコード）を、MVP セットが作って渡すための要件と設計。要件と構成の概要（`requirements-overview.md`）の決定事項 36 から参照する。

## 1. 位置づけ

- 料金の体系は、**テナント単位のテナント利用料**と、**回線単位のサービス利用料**で、どちらも月額。
- MVP セットは料金を計算しない。外部のシステムが料金の計算に使う記録を作り、ファイルにして渡す（オフラインチャージングの考え方）。
- 3GPP との対応: 課金の事実が起きる所（CTF）は aka-ossbss（テナントと回線の登録・状態の変化）と aka-radius（認証と Accounting）、記録を作ってファイルにする所（CDF / CGF）は aka-ossbss の課金レコードの生成、課金のシステム（BD）は外部のシステム。
- 参考にした規格: TS 32.240（課金の仕組み）、TS 32.297（CDR のファイルと受け渡し）、TS 32.298（CDR の項目）、TS 32.252（WLAN の課金）。形式（ASN.1）はまねず、完全性・重複の防止・ファイルの通し番号・遅れて届く記録・月またぎの扱いの考え方を借りる。
- 料金が定額なので、記録の中心は**状態の事実**（いつからいつまで、どの状態で存在したか）。利用の事実（認証・Accounting）は、「使ったかどうか」の判断の材料と、問い合わせへの備えとして出す。

## 2. 範囲

## 4. 用語

| 用語 | 意味 |
|---|---|
| 回線 | IMSI 1 つ |
| 対象月 | 日本時間のその月の 1 日 0 時から、翌月 1 日 0 時まで |
| 締め | 翌月 1 日の日本時間 6 時。対象月の月次のファイルを作る時刻 |
| 課金の事実 | 課金の判断の材料になる出来事（状態の変化、利用、数量） |
| 課金レコード | 課金の事実をまとめた CSV の 1 行 |
| 月次のまとめ | 対象月の CSV と manifest をまとめた ZIP を、PGP で暗号化したファイル |
| manifest | 月次のまとめの中の、CSV ごとの通し番号・件数・ハッシュを書いた目録 |
| 訂正のレコード | 締めの後に分かった差分で、前の月までのレコードを置き換える行 |

## 5. 課金の事実

### 5.1 状態の事実（aka-ossbss）

加入者・テナントの変更の経路は aka-ossbss → aka-provisioner だけなので（要件と構成の概要 §6.4）、aka-ossbss が操作の成功のたびに記録する。台帳の更新と同じ DB のトランザクションで、追記だけの表（`charging_events`）に書く。

| 事実 | 内容 |
|---|---|
| テナント | 作成、名前・外部の顧客番号の変更、削除 |
| 回線の登録 | vecgen 側・radius 側それぞれの登録（一括投入ではジョブの ID つき） |
| 回線の状態の変化 | vecgen 側・radius 側それぞれの Active / Inactive / Terminated の変化（Terminated からの戻しを含む） |
| テナントの付け替え | 回線の所属するテナントの変化 |
| 回線の物理削除 | vecgen 側・radius 側それぞれ |
| 突き合わせによる補い | 台帳と下流の突き合わせで見つけたずれを直したとき（理由つき） |

### 5.2 利用の事実（aka-radius）

aka-radius が、認証の成功と Accounting から、**IMSI・テナント・日（日本時間）ごとの利用の集計**を作る。テナントはエッジの刻印（要件と構成の概要 §8）から取る。

| 項目 | 元 |
|---|---|
| 認証の成功の回数 | auth-server の Access-Accept |
| セッションの数 | Accounting-Start の数 |
| 利用の時間（秒） | Accounting の Acct-Session-Time の増分 |
| 送受信の量（オクテット） | Accounting の Acct-Input-Octets / Acct-Output-Octets（Gigawords を含む）の増分 |

- 日の割り当ては、Accounting の Event-Timestamp があればその時刻、なければ受け取った時刻の日本時間の日付による。月をまたぐセッションは、増分をそれぞれの日に割り当てるので、月の境目で自然に分かれる。
- 集計はデータ面の Valkey に 7 日だけ持つ（それより遅れて届いた Accounting は集計に入れない。ログには残る）。aka-ossbss が毎日（日本時間 3 時。`OSSBSS_USAGE_IMPORT_AT`）と締めの前に、aka-provisioner を通して前の 7 日分を読み直し、PostgreSQL に残す。締めの後に変わった分は、次の締めで訂正のレコードにする。

### 5.3 数量の事実（aka-ossbss）

テナントごとの数量（回線の数、AP・グループ・持ち込みの CA の数、エッジへの配置の数）は、台帳とエッジの台帳から、月末の値と月の中の最大の値を出す。最大の値は、状態の事実の記録から計算する。

## 6. 時刻と日数

- レコードの時刻は RFC 3339 の形で、日本時間（`+09:00`）で書く（決定事項 15）。
- 「〜だった日数」は、対象月の日本時間の日付のうち、その状態だった時刻が少しでもある日の数とする。例: 10 月 31 日 23 時に Active にした回線は、10 月の Active の日数が 1 になる。
- 全ノードの時刻は NTP で合わせる（日の割り当てと締めの正しさのため）。

## 7. ファイル

### 7.1 月次のまとめ

締めのときに、対象月ごとに次の CSV と manifest（目録）を 1 つの ZIP にまとめ、その ZIP を PGP で暗号化する（決定事項 6・16）。ダウンロードは月に 1 回で済む。

| ZIP の中のファイル | 中身 |
|---|---|
| `events.csv` | 対象月の状態の事実（§5.1）の全件 |
| `lines.csv` | 回線ごとの月次のレコード（§7.4） |
| `tenants.csv` | テナントごとの月次のレコード（§7.5） |
| `lines_adj.csv` | 前の月までの `lines` の訂正のレコード（§7.6）。訂正がなければ、ヘッダーだけのファイル |
| `manifest.csv` | 上の 4 つのファイルの制御の情報（§7.3） |

- まとめのファイルの名前: `charging_<対象月 YYYYMM>_<通し番号 6 桁>_v<版>.zip.pgp`（例 `charging_202611_000001_v1.zip.pgp`）。
- 通し番号は月次のまとめごとに 1 から続く（欠けがないことで、取り込み漏れが分かる）。作り直したまとめは、通し番号を変えずに版を上げる（中の 4 つのファイルをまとめて作り直す）。
- ZIP は一般的な形（Deflate）で、ZIP 自体の暗号化は使わない（暗号化は PGP で行う）。

### 7.2 CSV の形

- RFC 4180 の形（改行は CRLF、値に `,`・`"`・改行があれば `"` で囲む）。UTF-8 で BOM なし。
- 1 行目は列の名前（ヘッダー）、2 行目からがデータ。すべての行が同じ列を持つ（一般的な道具でそのまま読める）。
- 空の値は空の文字列。真偽値は `true` / `false`。

### 7.3 manifest

`manifest.csv` は、ZIP の中の CSV ごとに 1 行を持つ CSV（形は §7.2 と同じ）。

| 列 | 内容 |
|---|---|
| `file_name` | ZIP の中のファイルの名前（例 `lines.csv`） |
| `kind` | ファイルの種類（`events` / `lines` / `tenants` / `lines_adj`） |
| `period` | 対象月（`YYYY-MM`） |
| `sequence` | 月次のまとめの通し番号 |
| `version` | 版 |
| `record_count` | データの行の件数（ヘッダーを除く） |
| `sha256` | ファイル全体の SHA-256（16 進の小文字。`sha256sum` で確かめられる） |
| `created_at` | 作った時刻 |
| `format_version` | 出力の形の版（例 `1.0`。列を足したら上げる） |

### 7.4 `lines.csv`（回線ごとの月次）

回線とテナントの組ごとに 1 行。月の途中でテナントの付け替えがあった回線は、テナントごとの行に分ける（決定事項 17）。利用の行は集計の刻印のテナントのまま（決定事項 23）なので、登録と違うテナントの行（`registered_days` が 0）と、刻印のない行（`tenant_id` が 0）がありうる。

| 列 | 内容 |
|---|---|
| `record_id` | `L-<YYYYMM>-<IMSI>-<テナントの ID>`（同じ月・回線・テナントで必ず同じ。作り直しても変わらない） |
| `period` | 対象月 |
| `imsi` | IMSI |
| `tenant_id` / `tenant_external_id` | テナントの ID と外部の顧客番号 |
| `line_external_id` | 回線の外部の番号（任意） |
| `registered_days` | その月にそのテナントで登録されていた日数（vecgen 側か radius 側のどちらかがあれば） |
| `radius_active_days` / `vecgen_active_days` | それぞれの側で Active だった日数 |
| `radius_state_start` / `radius_state_end` | 月初と月末（またはそのテナントを離れたとき）の radius 側の状態（未登録は空。月の途中で付け替えて来たテナントの行の月初は空） |
| `vecgen_state_start` / `vecgen_state_end` | 同じく vecgen 側 |
| `first_registered_at` / `deleted_at` | その月の中での登録（両側ともなかった状態から）と削除（両側ともなくなった）の時刻（なければ空。何度かあれば、登録は最初、削除は最後） |
| `auth_success_count` | 認証の成功の回数 |
| `session_count` / `session_seconds` | セッションの数と利用の時間 |
| `input_octets` / `output_octets` | 送受信の量 |
| `usage_complete` | その行の登録されていた日のうち、利用の集計を取り込めなかった日があれば `false`。データ面が止まっていた間の欠けは見分けられない（決定事項 13 のとおり取り決める） |

### 7.5 `tenants.csv`（テナントごとの月次）

| 列 | 内容 |
|---|---|
| `record_id` | `T-<YYYYMM>-<テナントの ID>` |
| `period` / `tenant_id` / `tenant_external_id` / `tenant_name` | 対象月とテナント（名前は月末の値） |
| `created_at` / `deleted_at` | その月の中での作成・削除の時刻（なければ空） |
| `existed_days` | その月にテナントが存在した日数 |
| `lines_end` / `lines_max` | 回線の数（月末、月の中の最大。どちらかの側で登録されているもの） |
| `radius_active_lines_end` / `radius_active_lines_max` | radius 側で Active の回線の数 |
| `aps_end` / `groups_end` / `brought_cas_end` / `placements_end` | AP・グループ・持ち込みの CA・エッジへの配置の数（月末） |

### 7.6 `lines_adj.csv`（訂正）

`lines.csv` と同じ列に、次の 2 列を足す。値は、訂正した後の行の全体（差分ではなく置き換え）。`record_id` はこの訂正の行の番号（`A-<このファイルの対象月 YYYYMM>-<IMSI>-<テナントの ID>`）、`period` は置き換える行の月。

| 列 | 内容 |
|---|---|
| `adjusts_record_id` | 置き換える元の `record_id` |
| `adjust_reason` | `late_usage`（締めの後に届いた利用、または取り込めなかった日を後から取り込んだ） |

- 訂正は、毎月の締めのときに、前の月の行と今の利用の集計を比べ、違う行だけを出す（利用は 7 日までしか変わらないので、比べるのは前の月だけ。元の行は変えない）。
- `events.csv` と `tenants.csv` の訂正は MVP では作らない（決定事項 19）。突き合わせで状態の事実を補ったときは、補いの事実を見つけた時刻の月の `events.csv` に出し、見つけた時刻の日から数える。前の月の行は直さない（決定事項 22）。テナントの数量の訂正は、必要になったら足す。
- 作り直しは、保存した月次の値から同じ行を作るので、訂正の行を増やさない（決定事項 25）。

### 7.7 `events.csv`（状態の事実）

| 列 | 内容 |
|---|---|
| `record_id` | `E-<事実の通し番号>`（`charging_events` の番号。作り直しても変わらない） |
| `event_time` | 起きた時刻 |
| `event` | `tenant_created` / `tenant_updated` / `tenant_deleted` / `line_registered` / `line_state_changed` / `line_tenant_moved` / `line_deleted` / `reconciled` |
| `side` | `vecgen` / `radius`（回線の事実のとき） |
| `tenant_id` / `tenant_external_id` | テナント（付け替えのときは移った先） |
| `imsi` / `line_external_id` | 回線（回線の事実のとき） |
| `from` / `to` | 変化の前と後（状態、付け替えの元と先のテナントの ID、名前、外部の顧客番号。`tenant_updated` の外部の顧客番号の変更は、`reason` が「外部の顧客番号の変更」） |
| `operator` | 操作した人（一括投入ではジョブを登録した人） |
| `job_id` | 一括投入のジョブの ID（あれば） |
| `trace_id` | `X-Trace-ID` |
| `reason` | 理由（Terminated からの戻し、突き合わせの補いなど。あれば） |

## 8. 作り

### 8.1 置き場所

| 役目 | ノード |
|---|---|
| 状態の事実の記録、利用の集計の取り込み、月次の計算、ファイルの生成と暗号化、保存、画面 | aka-ossbss（PostgreSQL） |
| 利用の集計（IMSI・テナント・日ごと、7 日） | aka-radius（auth-server と acct-server が Valkey に足し込む。取り出しの API を管理API に足す） |
| 利用の集計の中継 | aka-provisioner（中身は解釈しない） |

### 8.2 締めの流れ

1. 毎日の日本時間 6 時に aka-ossbss のジョブが動き、締めていない過去の月を古い順に締める（ふつうは翌月 1 日の 6 時。決定事項 24）。通し番号は締めのときに割り当てる。
2. 前の 7 日分の利用の集計を取り込む（取り込めなかった日があれば、その日に登録されていた回線の `usage_complete` を `false` にする。取り込みに失敗しても締める）。
3. 前の月の月末の値（月初の状態）と対象月の状態の事実から、回線とテナントの月次の値を計算する。最初の月は事実だけで計算する。
4. 前の月の行と今の利用の集計を比べて、訂正のレコードを作る。
5. 4 つの CSV と manifest を ZIP にまとめる。平文はディスクに書かず、CSV を作りながら ZIP に書き、その ZIP を流しながら PGP で暗号化し、暗号化したものだけを保存する（ZIP は後ろから読み返さずに書ける形で作る）。manifest のハッシュは、CSV を書きながら計算する。
6. 生成の結果（件数、平文のハッシュ、使った公開鍵のフィンガープリント）を記録し、監査ログに残す。

- 回線 20 万件の計算とファイルの生成は、締めから 30 分以内（案）に終える。規模の試験で確かめる。
- 状態の事実と利用の集計は PostgreSQL に 13 か月残すので、ファイルはいつでも作り直せる（§8.3）。

### 8.3 PGP の公開鍵

- システム管理者が画面から登録・更新する。使える鍵は 1 つ（今の鍵）。
- 登録のときに、暗号化に使える鍵（副鍵）があるか、期限が切れていないか、鍵の強さ（RSA 3072 ビット以上、または Curve25519）を確かめ、フィンガープリントを画面に出す。
- 鍵を入れ替えると、次に作るファイルから新しい鍵を使う。前に作ったファイルは古い鍵のまま残す。システム管理者は、前の月のまとめを今の鍵で作り直せる（版を上げる。決定事項 18）。
- 鍵の期限が近い（30 日）とき、または締めの前（毎月 25 日から）に鍵が登録されていないとき、鍵がなくてファイルを保留しているときは、画面と監視（`CHARGING_KEY_WARN`）で警告する。鍵を登録すると、保留していた月のファイルをすぐ作る。
- 実装には OpenPGP のライブラリ（Go では ProtonMail の go-crypto）を使う。

### 8.4 ダウンロード

- aka-ossbss の画面に「課金レコード」の画面を足す。月次のまとめの一覧（対象月、通し番号、版、中のファイルごとの件数、作った時刻、鍵のフィンガープリント）と、ダウンロードを出す。
- ダウンロードできるのはシステム管理者と運用担当だけ。ダウンロードのたびに、誰が・いつ・どのファイルかを監査ログに残す。
- 画面の入口は Cloudflare Access（今の作り）。

### 8.5 保存

- 状態の事実、利用の集計（日ごと）、月次の値、ファイル（暗号化したもの）は 13 か月残し、それより古い月を消す（決定事項 26）。利用の集計は月ごとのパーティションにして、古い月は DROP で消す。
- 課金レコードの表とファイルは、PostgreSQL のバックアップ（要件と構成の概要 §15）に含める。

## 9. 正しさの守り

| 心配 | 守り |
|---|---|
| 状態の事実の漏れ | 台帳の更新と同じトランザクションで記録する。台帳と下流の定期の突き合わせでずれを見つけたら、見つけた時刻の補いの事実（`reconciled`）を記録する（決定事項 22） |
| 重複 | `record_id` は同じ月・同じ対象で必ず同じ値にする（作り直しても変わらない）。外部のシステムは `record_id` で重複を除ける |
| ファイルの取り込み漏れ | 月次のまとめの通し番号が続いていることで分かる |
| ファイルの壊れ・改ざん・途中で切れること | PGP の完全性の検査。manifest の件数と SHA-256 |
| 遅れて届く利用 | 締めの後の分は翌月の訂正のレコードにする |
| データ面の停止 | 利用の集計が欠けた回線を `usage_complete=false` で示す |
| 時刻のずれ | 全ノードを NTP で合わせ、ずれを監視する |
| 締めの失敗 | 失敗を監視で知らせる（`CHARGING_CLOSE_ERR`・`CHARGING_FILE_ERR`）。1 つの月の締めは 1 つのトランザクションで、次の定刻か手で締め直す。システム管理者が画面から作り直せる |

## 12. 試験

| 場面 | 確かめること |
|---|---|
| 月の境目 | 月末の 23 時台・月初の 0 時台の状態の変化が、正しい月の日数に入ること。月をまたぐセッションの利用が、それぞれの月に分かれること |
| テナントの付け替え | 月の途中の付け替えで、回線の行がテナントごとに分かれること |
| 削除と再登録 | 同じ月に削除して登録し直した回線の日数 |
| 締めの後の Accounting | 翌月の `lines_adj` に出ること |
| データ面の停止 | 利用の集計の欠けが `usage_complete=false` になること |
| 鍵の入れ替えと作り直し | 新しい鍵で復号できること。作り直したファイルの `record_id` が同じで、版が上がること |
| ファイルの形 | 外部の一般的な道具（`gpg` での復号、`unzip`、`sha256sum`、表計算や CSV の読み込み）で読め、manifest の件数と SHA-256 が合うこと。aka-mvpset に検証の道具を置く |
| 規模 | 回線 20 万件・テナント 1,000 で、締めが目標の時間に終わること |

## 14. 確認事項（2026-10-25 にすべて合意。決定事項 14〜21）

E3 は、最初の推奨（同じ CSV の最後の行に制御のレコードを置く）を改め、ZIP と manifest にした。最後の行に制御のレコードを置く形は、固定長のバッチのファイル（銀行の振込のフォーマットなど）では定番だが、CSV ではすべての行が同じ列を持つ前提なので、取り込む側で最後の行を外す処理が要り、ハッシュの確かめ方も複雑になるため。

| # | 事項 | 推奨 |
|---|---|---|
| E1 | `events` のファイルを日次で作るか | 作らない（月次だけ）。ファイルは画面から手で取るので、毎日のファイルは手間になるため |
| E2 | レコードの時刻の書き方 | 日本時間（`+09:00`）で書く。月の区切りが日本時間なので、外部のシステムで扱いやすいため |
| E3 | 制御の情報の置き場所 | 月の CSV と manifest を 1 つの ZIP にまとめて PGP で暗号化する（CSV は素直な形のまま、ダウンロードは月に 1 回） |
| E4 | 月の途中でテナントを付け替えた回線 | 回線の行をテナントごとに分ける（どちらのテナントに請求するかを外部のシステムが決められるように） |
| E5 | 鍵を入れ替えたときの前のファイル | そのまま残し、システム管理者が今の鍵で作り直せるようにする（版を上げる） |
| E6 | `events`・`tenants` の訂正 | MVP では作らない。テナントの数量の訂正は、必要になったら足す。（当初の「突き合わせの補いを `lines_adj` で直す」は、決定事項 22 で「見つけた時刻の日に数え、前の月の行は直さない」に改めた） |
| E7 | 利用の集計をデータ面に持つ日数 | 7 日。回線 20 万件がすべて毎日使ったとしても、Valkey で数百 MB に収まる見込み（規模の試験で確かめる） |
| E8 | 鍵が登録されていないときの締め | 計算はして結果を DB に残し、ファイルの生成は鍵が登録されるまで保留にして警告する（平文のファイルは作らない） |
