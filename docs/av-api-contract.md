# 認証ベクターAPI の契約（下書き）

- 作成日: 2026-10-25
- 契約の版: 1.0.0-draft（§13）
- 状態: 下書き。§15 の確認事項は 2026-10-25 にすべて合意した（§3.2 の決定事項 1〜10）。
- 位置づけ: 認証ベクターを作るノード（aka-vecgen と、同じ契約を実装した他のノード）と、それを呼ぶノード（aka-radius）の間の約束の正本。要件と構成の概要（`requirements-overview.md`）の §7 と決定事項 4・5・17 から参照する。機械で読める定義は `openapi/av-api.yaml`。

## 1. 位置づけ

- aka-radius は鍵（Ki / OPc）を持たず、認証のたびに認証ベクターを外のノードから取る（概要の決定事項 5）。そのノードを本書では**取得先**と呼ぶ。MVP の取得先は aka-vecgen で、同じ契約を実装したノードに差し替えたり、並べて使ったりできる（決定事項 4）。
- 本書は、取得先を差し替えても aka-radius を変えずに済むように、両側が守ることを実装から独立に決める。aka-vecgen だけが知っていること（SQN の方式、鍵の保存、許可クライアントの持ち方）は書かない。
- 3GPP TS 29.503 Nudm_UEAU の GenerateAv（HSS 向けの認証ベクターの生成）をもとにする。パス・項目名・値の範囲は TS 29.503 v18.4.0 の OpenAPI の定義に合わせ、違いは §12 にまとめる。
- もとにしたのは aka-only-server の認証ベクターAPI 0.2.0-draft。MVP では一般的な拒否（§9.2）などで振る舞いが変わるので、新しい大きい版（1.0.0）にし、PoC セットとの互換は持たせない。

## 4. 用語

| 用語 | 意味 |
|---|---|
| 取得先（サーバー） | 認証ベクターを作って返すノード。aka-vecgen など |
| クライアント | 取得先を呼ぶノード。MVP では aka-radius（の中でベクターを取る部品） |
| ベクター | RAND・XRES・AUTN と、CK・IK（EAP-AKA、UMTS-AKA）または CK'・IK'（EAP-AKA'）の組 |
| 一般的な拒否 | 加入者の有無や状態を区別しない拒否の応答（§9.2） |
| ネットワーク名 | EAP-AKA' の鍵の導出（RFC 9048 §3.3）と AT_KDF_INPUT に使う名前。WLAN からの接続では `WLAN`（TS 24.302） |

「しなければならない」「してはならない」は必須、「する」は推奨（守らない理由があれば、その実装の文書に書く）とする。

## 6. 認証ベクターの生成（GenerateAv）

```
POST {基底の URL}/{supi}/hss-security-information/{hssAuthType}/generate-av
Content-Type: application/json
X-Trace-ID: <任意>
```

### 6.1 パスの値

| 値 | 内容 |
|---|---|
| `supi` | `imsi-<IMSI>`（数字 5〜15 桁）。他の形の SUPI（`nai-` など）は扱わない |
| `hssAuthType` | `eap-aka` / `eap-aka-prime` / `umts-aka`。ボディの `hssAuthType` と対応していなければならない（`umts-aka` は TS 29.503 にない拡張） |

### 6.2 リクエスト

| 項目 | 必須 | 内容 |
|---|---|---|
| `hssAuthType` | 必須 | `EAP_AKA` / `EAP_AKA_PRIME` / `UMTS_AKA` |
| `numOfRequestedVectors` | 必須 | 1〜5（§7） |
| `resynchronizationInfo` | 任意 | 再同期のときに `rand`（16 バイト）と `auts`（14 バイト）を入れる（§8） |
| `anId` | `EAP_AKA_PRIME` で必須 | ネットワーク名（§6.4）。他の認証タイプでは無視する |
| `requestingNodeType`、`servingNetworkId`、`supportedFeatures` | 任意 | 取得先は受け取ってよいが、使わない |

- 値のバイト列は 16 進の文字列で表す。取得先は小文字で返し、両側とも大文字も受け付けなければならない。
- 取得先は、知らない項目を無視しなければならない（拒否しない）。クライアントも、応答の知らない項目を無視しなければならない。将来の小さい版で項目を足せるようにするため。
- ボディの大きさの上限は 64 KiB とする（取得先はそれを超えるボディを 400 で拒否してよい）。

### 6.3 応答（200）

```json
{
  "hssAuthenticationVectors": [
    { "avType": "EAP_AKA", "rand": "…", "xres": "…", "autn": "…", "ck": "…", "ik": "…" }
  ]
}
```

| 認証タイプ | 配列の要素 | 項目 |
|---|---|---|
| `EAP_AKA`、`UMTS_AKA` | AvImsGbaEapAka | `avType`、`rand`、`xres`、`autn`、`ck`、`ik` |
| `EAP_AKA_PRIME` | AvEapAkaPrime | `avType`、`rand`、`xres`、`autn`、`ckPrime`、`ikPrime` |

| 値 | 長さ |
|---|---|
| `rand`、`autn`、`ck`、`ik`、`ckPrime`、`ikPrime` | 16 バイト（16 進 32 桁） |
| `xres` | 4〜16 バイト（16 進 8〜32 桁。TS 29.503 と同じ。Milenage では 8 バイト） |

- 取得先は、要求した数ちょうどのベクターを、SQN の小さい順に並べて返さなければならない。
- クライアントは、要素の数・`avType`・各値の長さを確かめ、合わなければ契約違反（§9.3）として扱わなければならない。
- 取得先は `Cache-Control: no-store` を付ける。
- ベクターの値（特に CK・IK・CK'・IK'・XRES）は、両側ともログに出してはならない。

### 6.4 EAP-AKA' とネットワーク名

- EAP-AKA' では、クライアントは `EAP_AKA_PRIME` で要求し、取得先が導出した CK'・IK' を受け取る。`EAP_AKA` で CK・IK を受け取って自分で導出してはならない（CK・IK を取得先の外に出さないため。HSS が接続網の名前で CK'・IK' を導出して渡す 3GPP の作りと同じ）。
- クライアントは `anId` にネットワーク名を入れて送らなければならない。同じ値を AT_KDF_INPUT に使う。
- 取得先は、クライアントごとに許すネットワーク名（既定は `WLAN` だけ）を持ち、許していない `anId` には 400（`OPTIONAL_IE_INCORRECT`）を返さなければならない。この検査は加入者を調べる前に行う（§9.2）。
- 鍵の導出は TS 33.402 Annex A.2（RFC 9048 §3.3）に従う。
- EAP-AKA' の AUTN は AMF の separation bit が 1 でなければならない（RFC 9048）。取得先は加入者の AMF をそのまま使い、確かめなくてよい。AMF を正しく入れるのは取得先の加入者の登録の役目。

## 7. ベクターの数と使い方

- 取得先は、`numOfRequestedVectors` の 1〜5 のどれにも応えなければならない（TS 29.503 の範囲。aka-radius 以外のクライアントのため）。
- クライアント（aka-radius）は、1 回の認証で 1 を要求し、受け取った 1 ベクターをその認証に使う。再同期のときは、その時点でもう 1 回要求する。
- クライアントはベクターを先取りして蓄えてはならない。理由は次のとおり。
  - 取得先で加入者を Inactive や Terminated にしても、蓄えたベクターで認証が通ってしまう。
  - 蓄えたベクターは鍵に準じる値で、クライアントの側に置く秘密が増える。
  - SQN の古いベクターは、端末の側で受け入れられなくなることがある（再同期が増える）。
- 取得先は、一度返したベクターを二度と返してはならない（同じ RAND・SQN の組を使い回さない）。

## 8. 再同期

1. クライアントは、端末から EAP-Response/AKA-Challenge の Synchronization-Failure（AT_AUTS）を受けたら、その直前の Challenge で送った RAND と、受け取った AUTS を `resynchronizationInfo` に入れて要求する。`hssAuthType` は直前の要求と同じにする。
2. 取得先は、AUTS の MAC-S を確かめ、SQN_MS を取り出し、加入者の SQN を SQN_MS をもとに置き換えてから、新しいベクターを作って返す。返すベクターの SQN は SQN_MS より大きくなければならない。
3. MAC-S が合わないときは、加入者の SQN を変えず、一般的な拒否（§9.2）を返さなければならない。
4. クライアントは、返ったベクターで新しい Challenge を送る。

- 取得先は RAND が自分の返したものかを確かめなくてよい（状態を持たない）。
- クライアントは、1 回の EAP の会話での再同期の回数に上限を設けなければならない（値は aka-radius の設計概要で決める。§3.2 の決定事項 9）。
- 再同期でベクターを作るまでの SQN の読み出し・置き換え・払い出しは、同じ加入者への他の要求と混ざらないようにしなければならない（§10）。

## 9. エラー

### 9.1 一覧

エラーの本文は TS 29.571 の ProblemDetails（`application/problem+json`）で、`cause` を必ず入れる。

| ステータス | `cause` | 意味 | クライアントの扱い |
|---|---|---|---|
| 400 | `INVALID_MSG_FORMAT` | JSON として読めない | 呼び出し側の誤り。その認証を拒否する |
| 400 | `MANDATORY_IE_MISSING` | 必須の項目がない（EAP-AKA' の `anId` を含む） | 同上 |
| 400 | `MANDATORY_IE_INCORRECT` | パスの値や必須の項目の値が正しくない、パスとボディの `hssAuthType` が対応しない、数が範囲の外 | 同上 |
| 400 | `OPTIONAL_IE_INCORRECT` | 任意の項目の値が正しくない、許していない `anId` | 同上。設定の食い違いなので、取得先ごとに目立つログを出す |
| 403 | `AUTHENTICATION_REJECTED` | 一般的な拒否（§9.2） | その認証を拒否する |
| 500 | `SYSTEM_FAILURE` | 取得先の中の誤り | 一時的な誤り（§9.3） |
| 501 | `AUTH_TYPE_NOT_SUPPORTED` | 対応していない認証タイプ（`eps-aka` など）。TS 29.503 にない値 | 設定の誤り。その認証を拒否する |
| 503 | `NF_CONGESTION` | 取得先が一時的に応えられない（起動の途中、保存先に届かないなど）。返すかは任意 | 一時的な誤り（§9.3） |

- 取得先は、本書にないステータスを返してはならない（パスが違うときの 404 と、メソッドが違うときの 405 を除く）。
- 5xx の `detail` に中の誤りの文（保存先のエラーの文など）を入れてはならない。

### 9.2 一般的な拒否

次の場合は、どれも**同じステータス・同じ本文**の応答を返さなければならない。

| 場合 | 取得先のログに残す理由（例） |
|---|---|
| 加入者が登録されていない | `not_found` |
| クライアントがその加入者の払い出しを許されていない | `client_not_allowed` |
| 加入者が Inactive | `inactive` |
| 加入者が Terminated | `terminated` |
| 再同期で AUTS の MAC-S が合わない | `auts_invalid` |
| 登録したクライアントが使えなくなっている（無効にした証明書で TLS が通る作りの場合） | `client_disabled` |

本文は次の固定の形とする（`detail` を入れない）。

```json
{"title":"Forbidden","status":403,"cause":"AUTHENTICATION_REJECTED"}
```

- AUTS の誤りを分けると、適当な AUTS で再同期を求めることで IMSI の有無を探れるので、これも含める。
- 判定の順は、(1) TLS でのクライアントの識別、(2) 加入者に依らない検査（パス・ボディの形、認証タイプ、`anId`）、(3) 加入者に依る検査（有無・許可・状態・AUTS）とする。(2) の誤り（400・501）は加入者の有無に関係なく同じに返り、(3) の誤りはすべて一般的な拒否になる。
- 一般的な拒否では、SQN を進めてはならない。
- 取得先は、理由・クライアント・IMSI・トレースID をログに残さなければならない（本文には出さない）。
- 応答にかかる時間の差（拒否の場合は鍵の計算をしないこと）は、計算 1 回分（数マイクロ秒）でネットワークの揺らぎに埋もれるので、契約では求めない。

### 9.3 クライアントの扱い

| 結果 | 分類 | 扱い |
|---|---|---|
| 200 で形が合う | 成功 | — |
| 400、403、501 | 確定した拒否 | その認証を拒否する。取得先の障害として数えない |
| 500、503、接続の失敗、TLS の失敗、タイムアウト | 一時的な誤り | その認証を拒否する。取得先の障害として数える（遮断器などに使ってよい） |
| 200 で形が合わない、本文のない 4xx、本書にないステータス | 契約違反 | その認証を拒否する。取得先の障害として数え、目立つログを出す |

- 「拒否する」の RADIUS での形（Access-Reject を返すか、応えずに再送を待つか）は aka-radius の設計で決める。

## 10. SQN について取得先が守ること

SQN の作り（方式、IND の扱い、保存）は取得先が決める。契約として守るのは次のことだけ。

- 同じ加入者に同時に要求が来ても、同じ SQN のベクターを二度作ってはならない。
- 同じ加入者に返すベクターの SQN は、要求の順に大きくならなければならない（1 回の応答の中では小さい順）。
- 再同期の後に返すベクターの SQN は SQN_MS より大きくなければならない。
- 一般的な拒否・400・501 では SQN を進めてはならない。5xx では進めてもよい（進んで飛ぶだけで、端末の側の害はない）。
- 要求は冪等ではない。同じ要求を 2 回送ると、別のベクターが 2 つ作られる。

## 11. タイムアウト、再試行、トレースID

### 11.1 タイムアウトと再試行

- クライアントは、要求 1 回のタイムアウト（接続を含む）を取得先ごとに設定できるようにする。既定は 3 秒。
- クライアントは、失敗した要求を自動で再試行しない（RADIUS の側の再送に任せる。再試行しても SQN が余分に進むだけで害はないが、遅い取得先に負荷を重ねるため）。
- 取得先は、概要 §4 の規模（加入者 20 万）で、ピーク 50 TPS の 2 倍の毎秒 100 要求のとき、応答の時間の 99 パーセンタイルを 200 ミリ秒以下にする（aka-vecgen は規模の試験で確かめる）。

### 11.2 トレースID

- クライアントは、1 回の認証を表すトレースID を `X-Trace-ID` ヘッダーで送る（印字できる ASCII 1〜64 文字）。aka-radius は、認証のトレースID をそのまま使う。
- 取得先は、受け取ったトレースID をその要求のログに残し、応答（エラーを含む）の `X-Trace-ID` ヘッダーで返さなければならない。ないときや形が違うときは自分で採番して（16 進 32 桁）、同じように扱う。

## 12. TS 29.503 との違い

| 項目 | TS 29.503 | 本契約 |
|---|---|---|
| 認可 | OAuth2.0、NRF | mTLS のクライアント証明書だけ |

## 13. 版の付け方

- 契約の版は `MAJOR.MINOR.PATCH` とし、本書の冒頭と OpenAPI の `info.version` を同じ値にする。
  - PATCH: 文の直し（振る舞いを変えない）。
  - MINOR: 互換を保つ追加（任意の項目、任意のステータスの追加など）。§6.2 の「知らない項目を無視する」で古い側も動く。
  - MAJOR: 互換を壊す変更。
- パスの `/nudm-ueau/v1` は TS 29.503 の API の版で、契約の版とは別に固定する（契約の MAJOR を上げてもパスは変えない）。
- 段階 0〜1 は `1.0.0-draft`。段階 2 で aka-vecgen が適合試験（§14）を通した時点で `1.0.0` にし、それ以降の変更は上の規則で版を上げる。
- 各実装は、どの版の契約に合っているかを自分の文書に書く。組み合わせの表（`versions.env`）に契約の版も記録する。
- MAJOR を上げる必要が出たときは、aka-radius の取得先の登録簿に契約の版を持たせ、新旧を並べて話せるようにする（その時に決める）。

## 14. 適合試験

本リポジトリの `conformance/av-api/` にある（Go のコマンド `av-conformance`。2026-10-27 に作った。使い方は同じディレクトリの README）。aka-vecgen は CI で、他の実装は導入のときに走らせる。

### 14.1 入力

| 入力 | 内容 |
|---|---|
| 取得先 | 基底の URL、サーバーの CA |
| クライアント証明書 | 2 つ。A はすべての試験用の加入者で許可、B はどの加入者でも許可しない |
| 試験用の加入者 | 本リポジトリで決めた表（試験用の PLMN `00101` の IMSI、TS 35.208 の試験用の鍵、AMF、状態）。実装は自分の管理の手段で先に入れておく |
| ネットワーク名 | クライアント A に `WLAN` だけを許しておく |

試験用の加入者の表（2026-10-27 に実装に合わせて決めた。正本は `conformance/av-api/fixture/fixture.go`）:

| IMSI | 鍵 | AMF | 状態 | 許可 |
|---|---|---|---|---|
| `001010000000001` | TS 35.208 の試験セット 1 | `8000` | Active | A |
| `001010000000002` | 同 3（EAP-AKA' の試験に使う） | `8000` | Active | A |
| `001010000000003` | 同 4 | `8000` | Inactive | A |
| `001010000000004` | 同 5 | `8000` | Terminated | A |
| `001010000000005` | 同 6 | `8000` | Active | なし |
| `001010000000099` | — | — | 登録しない | — |

- AMF はすべて separation bit を 1 にした（EAP-AKA' で使えるように。EAP-AKA でも差し支えない）。
- 試験セット 2 は使わない（aka-vecgen の試験の表では、試験セット 2 の値が試験セット 1 と同じになっていて、確かめた値が手元にないため）。
- aka-vecgen には `conformance/av-api/fixtures/aka-vecgen.sh` でまとめて入れられる。

### 14.2 項目

| # | 項目 | 確かめること |
|---|---|---|
| C1 | 形の誤り | §9.1 の 400 の各場合と 501。加入者の有無で応答が変わらないこと（`…001` と `…099` で同じ） |
| C2 | EAP-AKA と UMTS-AKA | 鍵から計算した値（XRES、CK、IK、AUTN の MAC-A）と一致し、AUTN から取り出した SQN が要求のたびに大きくなること |
| C3 | EAP-AKA' | CK'・IK' が `anId` のネットワーク名で導出した値と一致すること。`anId` がないと 400、許していない値で 400 |
| C4 | ベクターの数 | 1〜5 のそれぞれで、その数ちょうどが SQN の小さい順に返ること。0 と 6 で 400 |
| C5 | 再同期 | 試験の側で SQN_MS を決めて AUTS を作り、返ったベクターの SQN が SQN_MS より大きいこと |
| C6 | 一般的な拒否 | 未登録、クライアント B、Inactive、Terminated、MAC-S の合わない AUTS の 5 つが、ステータスと本文のバイト列まで同じであること。拒否の前後で SQN が進んでいないこと（次の成功の SQN で確かめる） |
| C7 | 同時の要求 | 同じ加入者に 50 並列で要求し、SQN がすべて異なること |
| C8 | トレースID | 送った値が返ること。送らないとき・形が違うときに採番した値が返ること。エラーの応答でも返ること |
| C9 | 知らない項目 | リクエストに知らない項目を足しても 200 になること |
| C10 | 接続 | 証明書なし・登録していない証明書が、TLS で拒否されるか一般的な拒否になること。TLS 1.1 以下でつながらないこと |
| C11 | 応答の形 | `Content-Type`、`Cache-Control: no-store`、16 進の小文字、`xres` の長さ |

- 外部の取得先で試験用の加入者を入れられないときは、鍵を使わない項目（C1・C4 の形・C6 の未登録とクライアント B・C8〜C11）だけを、運用者が渡した試験用の IMSI で行う。
- ログに詳しい理由が残ること（§9.2）は、試験では確かめず、導入の確認項目にする。
- 応答の時間（§11.1）は、適合試験ではなく規模の試験で確かめる。

### 16.1 aka-vecgen

| # | 改修 | 今の作り | 出どころ |

| V1 | 未登録・許可なし・Inactive・Terminated・AUTS の誤り・無効のクライアントを、§9.2 の固定の本文の 403 にする | 未登録は 404 `USER_NOT_FOUND`。403 は理由ごとに `detail` が違う。Inactive・Terminated の状態はまだない | A2 |
