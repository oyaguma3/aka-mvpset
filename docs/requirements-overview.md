## 1. 位置づけ

EAP-AKA の RADIUS 認証の PoC セット [eapaka-pocset](https://github.com/oyaguma3/eapaka-pocset) の `pocset-v1.0.0` と、RadSec の受け口 [radsec-edge](https://github.com/oyaguma3/radsec-edge)・独立CA [radsec-ca](https://github.com/oyaguma3/radsec-ca) をもとに、VPS に分けて置いて顧客を収容できる **MVP セット**を作る。

PoC セットでは「API と機能を変えない」としたが、MVP セットでは API・データモデル・名前を変えてよい。そのかわり、規模の保証値（§4）を試験で確かめることをリリースの基準にする。

MVP セットは、次の 7 つのリポジトリに同じ名前の注釈つきタグ（`mvpset-vX.Y.Z`）を付けて提供する。

| ノード | リポジトリ | もとにするもの |
|---|---|---|
| 認証ベクターの生成 | aka-vecgen | aka-only-server |
| RADIUS サーバー | aka-radius | eapaka-radius-server-poc |
| provisioner | aka-provisioner | eapaka-node-provisioner |
| OSS/BSS（統合BFF） | aka-ossbss | eapaka-ossbss-sample |
| RadSec の受け口 | radsec-edge | （名前を変えない） |
| 独立CA | radsec-ca | （名前を変えない） |
| MVP セット | aka-mvpset（本リポジトリ） | eapaka-pocset |

## 4. 規模と性能の要件

| 項目 | 保証値 |
|---|---|
| 加入者 | 200,000 |
| テナント | 1,000（1 テナントあたり加入者 20,000 まで） |
| AP（エッジに登録する RadSec のクライアント） | 1,000 |
| 認証 | ピーク 50 TPS、日中の平均 10 TPS |
| 同時のセッション | 20,000 |
| 一括投入 | 1 回 10,000 件まで（システムの上限）、30 分以内 |
| ログと Accounting の保存 | 3 か月 |

- 「AP 1,000」は、エッジに登録する RadSec のクライアントの数とする。aka-radius に登録する RADIUS クライアントはエッジ（と外形監視）だけになる。
- 参考の実測（2026-10-18、N100・16 GB の検証機）: 認証 1 回の p50 は 17 ms。8 並列で 217 回/秒、エッジを通して 185 回/秒、失敗 0。ピーク 50 TPS に対して 4 倍ほどの余裕がある。
- ログの量の見込み: 本PoC のログは認証 1 回あたり約 2.5 KB。日中 10 TPS が 9 時間続くと 1 日約 32 万回で約 0.8 GB、3 か月で約 75 GB（圧縮で 1/10 程度の見込み）。Accounting の分が加わる。

## 5. 構成

### 5.1 ノードの分類

| 分類 | ノード | 持つ秘密 | 機微度 |
|---|---|---|---|
| データ面 | aka-radius、aka-vecgen | Ki / OPc（vecgen）、Ki の KEK | 最も高い |
| 管理面 | aka-ossbss（+PostgreSQL、cloudflared）、aka-provisioner（+Valkey）、radsec-ca | CA の鍵と KEK、OSS/BSS の DB、一括投入の待ちのファイルの KEK | データ面に準じる |
| エッジ（2 台以上） | radsec-edge（+テナントごとの radsecproxy） | テナントのサーバー証明書の鍵 | 一段低い（Ki を持たない） |
| 監視 | Prometheus、Grafana、Alertmanager、blackbox_exporter、外形監視、踏み台 | 外形監視用の試験 SIM の鍵、運用用の WireGuard のハブの鍵 | 管理面に準じる |

### 5.2 配置

```
[AP] ─RadSec─> [エッジ ×2〜] ─WG(サービス)─> [データ面] aka-radius ─> aka-vecgen / 外部の取得先
[Box] ─RadSec─┘      │                            ▲
                     └─WG(サービス)─> [管理面] ────┘ 管理API（provisioner から）
                                       aka-ossbss ─> aka-provisioner ─> aka-vecgen / aka-radius / radsec-ca / radsec-edge
[運用者] ─Cloudflare Access─> aka-ossbss の画面
[監視用の PC] ─WG(運用)─> [監視・踏み台] ─WG(運用)─> 全ノード（SSH、node_exporter、ログの取得）
```

初めの見積もり（仮。§19 の計測で見直す）:

| ノード | vCPU / メモリー / SSD | 根拠 |
|---|---|---|
| データ面 | 2 / 4 GB / 50 GB | Valkey は加入者 20 万 ×2 とセッション 2 万で数百 MB の見込み。ログを 2 週間持つ |
| 管理面 | 2 / 4 GB / 40 GB | PostgreSQL、Valkey、CA。並べたビルドはしない（§17.3） |
| エッジ | 2 / 4 GB / 25 GB | 150 テナント（決定事項 25）。30% の余裕（約 1.1 GiB）で dockerd の膨らみも吸収する（§20.1） |
| 監視 | 2 / 2〜4 GB / 50 GB | Prometheus の保持期間による |

### 5.3 ネットワーク

- **サービス用の WireGuard**: エッジ ⇔ データ面（RADIUS）、エッジ ⇔ 管理面（エッジの管理API、CRL の取得）、管理面 ⇔ データ面（管理API）。ハブを置かず、ピアどうしで直接つなぐ。管理面をハブにして RADIUS を中継すると、管理面で RADIUS が平文になるため。
- **運用用の WireGuard**: 監視ノードをハブにする。SSH、node_exporter、ログの取得はこの経路だけを使う。運用者の監視用の PC もこの経路のピアにする。
- **公開する口**:

| ノード | 公開する口 |
|---|---|
| データ面 | なし。RADIUS はエッジのトンネルの IP からだけ受ける。予備の共有シークレットは空にする。認証ベクターAPI はノードの中だけ。管理API はサービス用のトンネルのアドレスにだけ結び付ける |
| 管理面 | なし（cloudflared が外向きにつなぐ） |
| エッジ | テナントの RadSec のポート（2083/tcp 系）と WireGuard |
| 監視 | WireGuard だけ |

- Docker が公開したポートは ufw を通らないので、nftables の `DOCKER-USER` で絞る。公開のアドレスは各ノードの設定で個別に結び付ける。
- エッジの Docker は `userland-proxy: false`（公開ポートごとの docker-proxy をなくす）と `live-restore: true`（dockerd を再起動してもコンテナと AP の接続を止めない）にする（決定事項 27）。
- 構成の確認項目に入れる既知の落とし穴: Docker が ufw を素通りすること、WireGuard のポートの取り違え、Docker の bridge を通ると送信元の IP が書き換わること。
- WireGuard のハンドシェイクが 180 秒途絶えたら異常とする（§14）。

## 6. 加入者のデータ

### 6.1 aka-vecgen

| 項目 | 内容 |
|---|---|
| IMSI | キー |
| Ki、OPc | 暗号化して保存（§12.1）。OP は扱わない |
| AMF、SQN、SQN の方式 | 方式は `inc1` / `inc32` / `inc33`。選び方の指針を文書にする（同じ USIM を別の生成源でも認証するなら、IND を固定する方式を選ぶ） |
| 許可クライアント | 払い出しを許す AV クライアント（mTLS で識別）の集合。空でもよい |
| 状態 | Active / Inactive / Terminated（§6.3） |

### 6.2 aka-radius

| 項目 | 内容 |
|---|---|
| IMSI | キー |
| 状態 | Active / Inactive / Terminated（§6.3） |
| 取得先 ID | 取得先の登録簿（ID、URL、クライアント証明書、サーバーの CA、タイムアウト）の ID。必須 |
| 認可ポリシー | ルールの配列。ルールはテナント（必須）、NAS-Identifier（テナントの中。`*` 可）、SSID、VLAN、Session-Timeout を持つ（§8） |

- RADIUS クライアント（エッジのトンネルの IP）は、「刻印を信頼する」の印を持つ（§8）。
- セッションには、刻印から読んだテナントの ID を残す（aka-ossbss のテナントの範囲のセッションの絞り込みに使う）。

### 6.3 状態

| 状態 | 認証 | 設定の変更 | 物理削除 | 移れる先 |
|---|---|---|---|---|
| Active | 通す（vecgen は払い出す） | できる | できない | Inactive、Terminated |
| Inactive | 拒否する | できる | できる | Active、Terminated |
| Terminated | 拒否する | できない | できる | Inactive（システム管理者だけ、理由を必須にする） |

- 状態の移り方は、各ノードの API が強制する。Terminated から戻す操作は専用の API にする。
- aka-vecgen と aka-radius の状態は独立している。画面では両方を並べて見せ、食い違いを示す。

### 6.4 aka-ossbss の台帳

- IMSI ごとに、テナントへの所属、vecgen 側と radius 側の有無と状態、取得先 ID、登録の日時と操作者、削除済みの印を持つ。鍵、SQN、認可ポリシーの中身は持たない。
- 正本は下流のままで、台帳は一覧・件数・絞り込みのための写しとする。
- 一覧のページ送りと絞り込み、件数、一括投入の前の「既にある」の確かめは台帳で行う。
- 下流の一括取得（IMSI を 500 件まで渡す。鍵は返さない）、下流の一覧の索引、セッションの取得で複数の IMSI を渡せることを入れる。セッションの開始時刻の索引は、20,000 件で測ってから決める（§19）。
- 台帳と下流を定期的に突き合わせ、ずれをシステム管理者の画面に出す。
- 加入者・認可ポリシーの変更の経路は aka-ossbss → aka-provisioner だけにする（下流の管理クライアントを aka-provisioner だけにする）。

## 7. 認証ベクターAPI の契約

契約の文章は `av-api-contract.md`、OpenAPI は `openapi/av-api.yaml`。版の付け方は契約の §13。

- 3GPP TS 29.503 Nudm_UEAU の GenerateAv をもとに、実装から独立した契約（OpenAPI と文章）を本リポジトリに置き、版を付ける。
- 契約に書くこと: mTLS によるクライアントの識別、EAP-AKA / EAP-AKA' / UMTS-AKA、要求できるベクターの数、再同期（RAND と AUTS）、エラー、タイムアウト、1 回の要求で 1 ベクターを使い、先取りしないこと。
- 未登録・許可されていない・Inactive・Terminated は、呼び出し側には同じ一般的な応答で返す（IMSI の有無を探られないため）。詳細な理由は、ベクターを作る側のログにだけ残す。
- 契約に合っているかを確かめる適合試験を本リポジトリに置き、aka-vecgen も他の実装も同じ試験で確かめる。

## 8. テナントの刻印と認可

### 8.1 刻印

| 項目 | 内容 |
|---|---|
| 値 | aka-ossbss のテナントの ID（番号。変わらず、使い回されない）を 10 進の文字列にしたもの（例 `42`）。slug は、消したテナントの slug が使い回されると古いポリシーが新しいテナントに当たるおそれがあるので使わない |
| 形 | RFC 2865 §5.26 の VSA（Vendor-Id 4 オクテット、Vendor-Type 1 オクテット、長さ、値） |
| 属性の番号 | Vendor-Type 1 = テナントの ID。2 以降は将来のために空けておく（どのエッジから届いたかは送信元のトンネルの IP で分かる） |
| Vendor-Id | 環境変数で指定する。MVP の既定は 32473（RFC 5612 の文書用）、実運用では IANA から取得した PEN |
| 付ける対象 | エッジに届く認証と Accounting のすべて（radsecproxy の `rewriteIn` は client ブロックで受けたすべてのパケットにかかる） |

- エッジの radsecproxy は、どの client ブロックでも、AP から届いた同じ VSA を取り除いてから（`removeVendorAttribute`）、テナントの ID を付ける（`addVendorAttribute`）。
- Vendor-Id と Vendor-Type は、エッジと aka-radius の両方で環境変数にする（既定 32473 と 1）。食い違うとすべて拒否になるので、両方とも起動のときに値をログに出す。

### 8.2 aka-radius での扱い

- RADIUS クライアントに「刻印を信頼する」の印を持たせ、印のあるクライアント（エッジ）から届いた刻印だけを使う。印のないクライアントから届いた刻印は、ないものとして扱う。
- 刻印が 2 つ以上届いたら拒否する（エッジでの取り除き漏れに備える二重の守り）。
- ルールを配列の順に評価し、テナント・NAS-Identifier・SSID がすべて一致した最初のルールを採る。テナントの条件があるルールで、刻印がないか使えないときは拒否する（fail-closed）。
- Accounting では、刻印のテナントの ID をセッションに残す。
- テナントの判定に NAS-Identifier の前方一致は使わない（slug にも AP の名前にも `-` が入るので、別のテナントに一致しうる）。NAS-Identifier の規則（AP の `<slug>-<AP の名前>`、全体で一意）は、ログの読みやすさのために変えない。

## 9. RadSec の受け口

### 9.1 エッジ

- radsec-edge の管理モード（エッジの設計概要の段階 4）を MVP に取り込む。テナントごとに radsecproxy のコンテナを立てる作りは変えない。
- 1 つのテナントを複数のエッジに置ける。AP は DNS のスロット（primary / secondary / tertiary）で複数のエッジを知る。
- テナントのポートは全体で一意に割り当て、範囲は 20000〜21999（2,000 個）とする。radsec-edge §8.1 の 20830〜20999（170 個）では保証値のテナント 1,000 を収容できないため（aka-ossbss の設計概要の決定事項 9。radsec-edge の文書は段階 4 で直す）。
- エッジ 1 台あたりのテナントの上限を aka-ossbss の配置の検査に入れる（既定は 4 GB のエッジで 150。決定事項 25）。

### 9.2 登録するもの

テナントには、次の 3 種類を登録できる（決定事項 33）。AP とグループは、どちらもテナントのクライアントCA（テナントごとの自己署名）の証明書を URI SAN で照合するので、同じテナントに混ぜて登録できる。

| 種類 | 証明書 | エッジでの照合 | NAS-Identifier | 最後の接続 | 1 つだけ止める |
|---|---|---|---|---|---|
| AP | radsec-ca が AP ごとに発行（AP が CSR を作る） | URI SAN `urn:<接頭辞>:nas:<テナント>:<AP>` | `<slug>-<AP の名前>` に置き換える | AP ごと | 証明書を失効させる |
| グループ | radsec-ca が発行し、AP のグループで共有する（Box を含む。§9.3） | URI SAN `urn:<接頭辞>:grp:<テナント>:<グループ>` | AP が送った値をそのまま通す（ないときは `<slug>-<グループ>`） | グループごと（送信元の IP つき） | 証明書を失効させる、またはブロックを消す |
| 持ち込みの CA（任意） | 業者の CA が AP ごとに発行（§9.4） | 共通のブロック（CA の束と CRL。CRL のない CA では業者の証明書の形も） | そのまま通す（ないときは `<slug>`） | 送信元の IP ごと | aka-radius の認可ポリシー（その NAS-Identifier を拒否）か業者の CRL |

- エッジは client ブロックを、AP、グループ、ヘルスチェック（probe）、共通のブロック（持ち込みの CA があるときだけ）の順に並べる。radsecproxy は TLS で証明書を確かめた後、書いた順に照らし合わせ、最初に一致したブロックを使う。共通のブロックはどの証明書にも一致しうるので必ず最後に置き、設定の生成で順番を固定し、生成するときにも確かめる。
- 共通のブロックがないテナントでは、どのブロックにも一致しない証明書（登録していないもの、消したもの）は拒否される（§20.2 の B1b・B2）。
- 持ち込みの CA を足す・外すのはシステム管理者だけ（共通のブロックができて、受ける範囲が広がるため）。
- エッジのテナントの tls ブロックは 1 つで、CA の束・`CRLCheck`・`PartialChain`（§9.6）はテナント全体で共通の設定になる。
- どのブロックの rewrite にも、刻印の取り除きと付与（§8.1）を入れる。
- 送信元のアドレスの範囲（任意。決定事項 35）: 拠点の IP が固定の顧客では、テナントごとに許す送信元を設定でき、そのテナントのすべてのブロックの `host` に入れる。
- テナントの中での NAS-Identifier の名乗りの偽りは受け入れる（テナントをまたぐ偽りは刻印で防ぐ）。
- 業者の AP が接続するたびに、共通のブロックより前のブロックの数だけ「一致しない」の行がログに出る。AP の多いテナントで持ち込みの CA を使うときは、ログの量に気をつける。

### 9.3 グループの証明書

radsec-ca がテナントのクライアントCA で発行した 1 枚の証明書を、AP のグループで共有して使う。業者の製品が「証明書と鍵を 1 組だけ入れ、AP のグループで共有する」作りのときの収容の形で、RadSec に対応しない AP をまとめる Box（§9.7）もこの形で受ける。

| 使い道 | 証明書を入れる単位 | 秘密鍵の置き場所 |
|---|---|---|
| UniFi | RADIUS のプロファイル | UniFi Network を通して、そのプロファイルを使う全 AP |
| Extreme（ExtremeCloud IQ） | RADIUS サーバーの定義（Trust Point） | クラウドを通して、RadSec の代理役の AP |
| Extreme（ExtremeCloud IQ Controller） | コントローラーの Trust Point | コントローラー |
| Aruba（証明書を差し替える場合） | AP グループ（Central） | Central を通して AP |
| Mist（証明書を差し替える場合） | 組織 | Mist のクラウドを通して全 AP |
| Box | Box 1 台 | Box |

| 項目 | 内容 |
|---|---|
| グループの名前 | AP の名前と同じ規則。テナントの中で一意で、AP の名前とも重ならない（CN が同じになるため） |
| 用途 | `box` / `unifi` / `extreme` / `aruba` / `mist` / `other`（表示と手順書の案内に使う。照合には使わない） |
| 証明書 | プロファイル `group-client`。CN `<slug>-<グループ>`、SAN（URI）`urn:<接頭辞>:grp:<テナント>:<グループ>`、clientAuth、730 日（短くもできる） |

流れ（管理モード）:

1. テナント管理者が aka-ossbss でグループを登録する（名前と用途）。
2. 顧客が手元で鍵と CSR を作る（用途ごとの手順書に openssl のコマンドを載せる。鍵の種類は製品が受け付けるもの）。鍵は顧客の手元から出さない（radsec-ca は鍵を作らない）。
3. CSR を aka-ossbss に出し、aka-provisioner を通して radsec-ca が署名する。
4. aka-ossbss から、グループの証明書、サーバーCA の証明書、接続先（スロットの名前とテナントのポート）、用途ごとの設定の手順を渡す。
5. aka-ossbss が、テナントを置いた全エッジにグループを送って反映する。
6. 顧客が製品に証明書・鍵・サーバーCA を入れる。

- **更新**: 同じグループの名前で新しい CSR に署名する（SAN が同じなので、エッジの設定は変わらない）。顧客が入れ替えた後で古い証明書を `superseded` で失効させる。新旧が両方有効な間はどちらでもつながる（§20.2 の B3〜B3d）。期限の 30 日前から画面と監視で知らせる。
- **グループを消すとき**: 証明書を `cessationOfOperation` で失効させ、ブロックも消す。
- **鍵の漏えい**: 鍵はグループの全 AP や業者のクラウドに置かれるので、AP ごとの証明書より漏れる経路が多い。被害がそのテナントに限られること（テナントごとの CA と刻印）が前提の守り。漏れたら新しい鍵で発行し直し、古い証明書を `keyCompromise` で失効させる。拠点の IP が固定の顧客には、送信元の範囲の設定を勧める。
- AP を 1 台ずつ見分けるのは NAS-Identifier の役目。用途ごとの手順書で、製品の NAS-Identifier の推奨の設定（AP の名前や MAC など）を案内する。

### 9.4 持ち込みの CA

業者の CA が AP ごとに証明書を発行する製品（Meraki、Mist の既定）を、その CA を信頼して受ける（決定事項 34）。

- **テナント専用であること**: 業者の組織ごとの CA に限る。1 テナント = 1 業者の組織とし、同じ CA（フィンガープリント）を 2 つのテナントに登録できないよう radsec-ca で検査する。全顧客で共通の CA（Aruba の工場出荷の証明書の CA など）は受けない（他の顧客の AP もつながり、テナントの刻印が付いてしまうため）。登録する人が「このテナント専用の CA であることを確かめた」と明示し、監査ログに残す。
- **信頼のさせ方**:

| CA の形 | 例 | 束に置くもの | `PartialChain` | CRL |
|---|---|---|---|---|
| 組織ごとの自己署名の CA | Mist の既定（推定） | その CA | 不要 | 取れれば必須。取れなければ下の扱い |
| 組織ごとだが自己署名でない CA | Meraki（PureCA）の RadSec 用の CA | その CA だけ（共通のルートと共通の中間 CA は置かない） | `on`（§9.6） | 必須（Dashboard API で取る） |
| 全顧客で共通の CA | Aruba の工場出荷の証明書 | — | — | 受けない |

- **Meraki の信頼の起点**: 組織の CA ではなく RadSec 用の CA を起点にする。要る CRL はその CA の CRL 1 つだけになる（§20.2 の C1・C4）。共通のルートを信頼すると、他の組織の Meraki の AP も通ってしまう（同 P2）。
- **CRL が取れる CA**: CRL を必須にする。持ち込みの CA と CRL の取得先は radsec-ca に登録し、radsec-ca が定期的に取り直して（URL、Meraki の Dashboard API、アップロード）、署名を確かめ、今の配布の口で配る。エッジは今と同じ口から取る（エッジからインターネットの業者の口へ出なくて済む）。Meraki の API キーは、顧客に読み取り専用の管理者のキーを出してもらい、radsec-ca が KEK で暗号化して持つ。
- **CRL が取れない CA（Mist の可能性）**: そのテナントだけ `CRLCheck off` にする。代わりに次の 2 つで守る（§20.2 の M1〜M5）。
  - 共通のブロックを業者の証明書の形（例: Mist の CN が MAC の 12 桁）で絞り、こちらが発行した証明書が共通のブロックに入らないようにする。
  - こちらが発行した証明書（AP・グループ・probe）の失効は、ブロックを消すことで行う（`CRLCheck off` では、失効させた証明書も TLS の検証を通るため）。
  - 業者の AP の失効は効かない（業者が失効の手段を出していないため）。1 台だけ止めるには aka-radius の認可ポリシーを使う。
- CRL のない CA が束にあっても、拒否されるのはその CA の証明書だけで、他の CA の証明書は巻き込まれない（§20.2 の C7・C7c）。
- 業者の CA の入れ替え（Meraki の Keeper から PureCA への移行のような）に備え、移行の間は新旧の CA を同じテナントに並べて登録できるようにする。

### 9.5 製品ごとの収容の方式

| 製品 | 収容の形 | 条件・注意 |
|---|---|---|
| Cisco Meraki MR（PureCA） | 持ち込みの CA（RadSec 用の CA を `PartialChain` で起点） | MR 33.1.2 以上。旧方式の Keeper（組織の自己署名 CA）は 2026-11 に廃止されるので扱わない。CRL は Dashboard API（`/organizations/{orgId}/wireless/devices/radsec/certificates/authorities/crls`。差分の CRL は使わない）。設定: シークレットは `radsec`、ポートはテナントのポート、Dashboard の「Test」は RadSec に使えない、Client Balancing と RADIUS proxy は使わない。NAS-Identifier は AP の名前か MAC を勧める（既定は「AP の MAC:SSID の番号」）。Called-Station-Id は既定（MAC:SSID の名前）のまま |
| Juniper Mist | 持ち込みの CA（組織の CA。自己署名と推定） | 組織の CA は Organization の Settings の「View Certificate」で取り出す。AP のファームウェア 0.8x 以上。CRL の有無は未確認（なければ §9.4 の CRL が取れない CA の扱い）。HPE による統合で PKI が変わらないかを見張る |
| Ubiquiti UniFi | グループ（RADIUS のプロファイルごと） | UniFi Network 8.4 以上、無線だけ。証明書・鍵・CA（サーバーCA）を PEM で入れる |
| Extreme（ExtremeCloud IQ / Controller） | グループ（Trust Point ごと） | ExtremeCloud IQ は RadSec の代理役の AP だけが外へつなぐ（送信元を絞りやすい）。証明書と鍵を入れる |
| HPE Aruba | グループ（証明書を差し替える） | RadSec の証明書は AP グループで 1 組で、顧客が使う他の RadSec の宛先と共用になる。差し替えても工場出荷の証明書を出し続けた事例がある（受入試験で確かめる）。工場出荷の証明書（全 Aruba で共通の CA）は受けない |
| Juniper Mist（差し替える場合） | グループ（組織で 1 組） | 組織の全 AP が同じ証明書になる |
| Box（RadSec に対応しない AP） | グループ（Box ごと） | §9.7 |
| RUCKUS、FortiAP、Panasonic AIRRECT ほか | 未調査 | 受けるときに調べる |

- どの製品も、2083 以外のポート（テナントのポート）を設定できるかを最初に確かめる（決定事項 35。設定できない製品は、今の作りでは収容できない）。
- 実機での確認（業者の証明書と CRL の中身、AP が送るチェーン、ポート、NAS-Identifier の実際の値、証明書の差し替えが効くか）は、機材が手に入るまで行わない（決定事項 31。§19）。

### 9.6 radsecproxy

- エッジの radsecproxy は、1.11.4 のソースに次の変更を加えてビルドする（Debian のパッケージはやめる。決定事項 32）。
  - tls ブロックごとのオプション `PartialChain`（on のとき、`CACertificateFile` の自己署名でない CA も信頼の起点にする。OpenSSL の `X509_V_FLAG_PARTIAL_CHAIN`）。
  - `PartialChain on` で `CRLCheck on` のときは、CRL の確認を相手の証明書（リーフ）だけにする。無改造の radsecproxy はチェーン全体を確かめる（`CRL_CHECK_ALL`）ので、起点にした CA そのものの CRL を求められ、正当な AP も拒否される（§20.2 の C1a・C2a）。起点にした CA は設定で信頼しているものなので、その失効は束から外すことで扱う。
- `PartialChain` を書かないテナントの振る舞いは無改造と同じ（§20.2 の P9）なので、すべてのテナントでこの版を使う。
- ソースの tar の SHA-256 を固定する。新しい版が出たら追いかけ、パッチを当て直してラボ（`verify/r10`）を通す。パッチは upstream に提案する。
- radsecproxy のチェーンの深さの上限は 5（`MAX_CERT_DEPTH`）。PartialChain で起点を近くに置くので、業者の階層が増えても影響を受けにくい（§20.2 の P10・P11）。
- 照合できるのは相手の証明書の CN と SAN だけで、発行者（Issuer）では絞れない。

### 9.7 RadSec に対応しない AP

- radsecproxy をもう 1 つ（貸与の Box など）置き、AP →（UDP の RADIUS）→ Box →（RadSec）→ エッジ とつなぐ。Box の証明書は、グループの証明書（用途 `box`）として radsec-ca が発行し、エッジはグループのブロックで受ける（§9.3）。
- Box は顧客の構内か VPN の中に置く。UDP の RADIUS をインターネットに通さない。
- Box の作り（イメージ、設定の生成）は §19 で決める。

## 10. 一括投入と一括の物理削除

### 10.1 ジョブ

| ジョブ | 画面で一律に選ぶもの | CSV の列 |
|---|---|---|
| vecgen への登録 | テナント、状態（Active / Inactive）、許可クライアント（空でもよい）、SQN の方式 | IMSI、Ki、OPc、AMF、SQN（AMF と SQN は空なら既定値） |
| radius への登録 | テナント、状態（Active / Inactive）、認可ポリシー、取得先 ID | IMSI |
| vecgen からの物理削除 | — | IMSI |
| radius からの物理削除 | — | IMSI |

- 使えるのはシステム管理者だけ。
- CSV は UTF-8、ヘッダー行あり。ヘッダーの形をジョブの種類ごとに固定し、窓口と合わないファイルを断る。
- 1 回 10,000 件まで（システムの上限）。
- 一律の設定は、ジョブの記録に残す。

### 10.2 待ち行列

- 対象（vecgen / radius）ごとに 1 本の待ち行列を持ち、それぞれ同時に 1 つのジョブだけを動かす。ジョブの登録は複数でき、登録した順に処理する。
- ジョブは aka-ossbss の中で動かし、aka-provisioner の 1 件ずつの API を呼ぶ。
- 待っている間のファイルは KEK で暗号化して DB に置き、完了・中断・取り消しのときに消す。
- aka-ossbss が止まると、動いていたジョブは「中断」になる。待っていたジョブは残る。

### 10.3 検証と実行

- **検証の段**: 全行を先に確かめる（形式、ファイルの中の IMSI の重複、件数の上限、台帳での所属の食い違い、削除の対象が Active でないこと）。1 行でも不合格があれば何も投入せず、行番号つきで誤りを示す。
- **実行の段**:
  - 同時に数件ずつ呼ぶ。行ごとの `Idempotency-Key` は、ジョブの ID と IMSI から作る。
  - 既にある IMSI は上書きせず「既にある」として数える（同じファイルの再投入が安全になる）。
  - 削除のとき、ない IMSI は飛ばして数える。
  - 下流に接続できない誤りが続いたら（案: 10 件）、自動で中断する。
  - 鍵の差し替えは一括の経路では行わない。
- **速さ**: 1 万件を 30 分以内（毎秒 5.6 件）。規模の試験で確かめ、届かなければ下流の一括作成を検討する。

### 10.4 中断と報告

- システム管理者はジョブを中断できる（取り消しだけで、再開はしない）。処理中の行を終えてから止め、処理済みの行は元に戻さない。同じファイルを投入し直せば、残りだけが処理される。
- ダッシュボードに、進み具合（率）、完了数、失敗数、待ちのジョブを出す。
- 結果と中断の報告（件数、失敗した行と未処理の行の一覧。鍵は含めない）を残し、監査ログの画面で見られるようにする。CSV でも取り出せる。
- 監査ログは、ジョブごとの開始・終了・中断と、行ごとの操作（ジョブの ID つき）を残す。下流への要求の `X-Trace-ID` にジョブの ID を入れて結び付ける。

## 11. 権限

aka-ossbss の役割（テナントユーザー・テナント管理者・運用担当・システム管理者）は変えない。MVP で加わる・変わる操作は次のとおり。

| 操作 | 使える役割 |
|---|---|
| 一括投入、一括の物理削除、ジョブの中断 | システム管理者 |
| Terminated から Inactive に戻す（理由を必須にする） | システム管理者 |
| 鍵（Ki / OPc）の個別の登録 | システム管理者 |
| 鍵の表示 | なし（画面から外す） |
| 削除済みの IMSI の登録し直しの承認 | システム管理者 |
| 状態の変更（Active ⇔ Inactive、Terminated へ） | 今の「停止・再開」と同じ役割 |

## 12. 鍵と秘密の値

### 12.1 保存時の暗号化

- aka-vecgen の Ki / OPc は AES-256-GCM で暗号化し、AAD に IMSI を入れて別の行への移し替えを防ぐ。KEK はファイル（Docker secrets）で渡し、DB には KEK の識別子だけを持つ。radsec-ca の KEK の作りと手順にそろえる。
- 一括投入の待ちのファイルも同じ方式で暗号化する。

### 12.2 鍵の経路

- 鍵が通るのは、一括投入（aka-ossbss → aka-provisioner → aka-vecgen）とシステム管理者の個別の登録だけ。通常の管理操作は、状態・許可・認可ポリシーだけを扱う。
- 鍵は、ログ、監査ログ、ジョブの結果に出さない。読み出しの API は既定で無効にする。

### 12.3 管理用の mTLS のピン

- 管理クライアントのフィンガープリント（ピン）を、再起動せずに読み直せるようにする。
- 新旧の 2 つを並べて登録する期間を設ける更新の手順と、鍵が漏れたときの差し替えの手順を、ノードを横断する運用手順書にまとめる。証明書の期限は監視する（§14）。

## 13. ログと監査ログ

- ログと Accounting は 3 か月保存する。ノードでは圧縮して 2 週間持つ。
- 運用者の監視用の PC が、運用用の WireGuard と踏み台を通して、定期的に取りに行く（rsync over SSH のプル型。PC の受信の口を開けない）。
- 監査ログ（各ノード）は、上限つきの保存先で押し出される前に、同じ仕組みで追記専用の保存先へ書き出す。
- Accounting の保存の層（Start は全量、Interim は間引く）と、「認証は成功したが通信できない」の切り分け（Acct-Start の有無）を運用ガイドに書く。
- `X-Trace-ID` で、aka-ossbss → aka-provisioner → 下流の記録をたどる手順を運用ガイドに書く。
- ログの IMSI のマスクは、既定をオフにする（今の作りは既定でオン。決定事項 26）。運用ガイドに「運用上、調査・解析のトレーサビリティを優先するため、IMSI のマスクの既定をオフとしているが、生の IMSI がログに出力されることを認識しておくこと」と注記する。ログを取りに行く監視用の PC にも生の IMSI が残るので、その PC の扱い（保管、アクセスできる人）も同じ注記に含める。

## 14. 監視

- 監視ノードに Prometheus、Grafana、Alertmanager、node_exporter（各ノード）、blackbox_exporter を置く。
- 見るもの: ノードの死活と OS の基本情報、コンテナの状態、HTTP の healthcheck、WireGuard のハンドシェイク、エッジの CRL の次の更新までの残り時間、証明書の期限、dockerd と containerd の RSS（エッジでは 400 MiB を超えたら警告。決定事項 28）。
- **外形監視**: 監視ノードから、AP の役の radsecproxy と EAP-AKA の試験用のクライアントで、エッジ → aka-radius → aka-vecgen の認証を定期的に最後まで通す。結果が届かないことも異常とする。試験用の SIM は専用のテナントと IMSI に分け、認可を最小にする。
- 監視ノードが止まったときに、VPS の事業者のコンソールから入る手順を用意する。
- アプリの KPI（認証の成否、遅延など）は、ログの event_id から作る（§19）。

## 15. バックアップと復旧

| 対象 | 置き場所 | 手段（案） |
|---|---|---|
| KEK（aka-vecgen、radsec-ca、一括投入） | 各ノードのファイル | DB とは別の場所にオフラインで保管する。失うと鍵や CA の作り直しになる |
| Valkey（aka-radius、aka-vecgen、aka-provisioner） | データ面、管理面 | AOF と定期のスナップショット |
| PostgreSQL（aka-ossbss） | 管理面 | `pg_dump` |
| SQLite（radsec-ca、radsec-edge） | 管理面、エッジ | 定期のコピー |

- 秘密の値の保管先・バックアップ・担当を 1 枚の表にし、VPS を 1 台失ったときの復旧手順を書く。
- 復元すると SQN が巻き戻るので、再同期で回復することを試験で確かめる。
- 目標とする復旧時点（RPO）と復旧時間（RTO）は §19 で決める。

## 16. 試験

### 16.1 規模の試験

- 加入者 20 万（ルールは平均 1.5 件）、AP 1,000、セッション 20,000 のデータで行う。
- ピーク 50 TPS を 30 分続けて失敗 0。
- 一括投入 1 万件が 30 分以内。
- 一覧・検索・ダッシュボードの応答の時間。

### 16.2 受入試験（顧客を収容するとき）

- RadSec の接続、実際の SIM での認証、他のテナントの IMSI が拒否されること、Accounting、無通信が長く続いたときの接続の維持、エッジが 2 台ならその切り替え。
- 証明書の受け渡しは CSR の方式を優先し、トラストアンカーにはフィンガープリントを添える。
- データ面と管理面が 1 台ずつであること（単一障害点）を顧客に説明し、了承を記録する。
- 既知の制約として、仮名による認証がないので無線の区間で IMSI が見えることを説明する。
- 業者の製品ごとに、§9.5 の条件（ポート、証明書と CRL、NAS-Identifier の設定、証明書の差し替えが効くか）を確かめる。持ち込みの CA では、テナント専用の CA であること（発行の範囲）を確かめる。

### 16.3 E2E

- `scripts/e2e.sh`（PoC セットのものを引き継ぐ）で、7 つのリポジトリの組み合わせを導入して認証の流れを確かめる。エッジを通す経路、テナントの刻印、状態による拒否を加える。

### 16.4 長い時間の試験（エッジ）

- radsec-edge を本物の形で 150 テナント動かし、整合ループ（1 分ごと）、全テナントのログの読み出し（1 分ごと）、healthcheck、定期の反映（捨てるコンテナ）を 24〜72 時間続け、dockerd と containerd の RSS を 1 時間ごとに記録する（決定事項 28）。
- dockerd を再起動して、radsecproxy のコンテナと AP の接続が止まらないこと（`live-restore`）、radsec-edge の agent がつなぎ直すことを確かめる。
- 増え方が大きければ、systemd の設定で dockerd に `GOMEMLIMIT` を与えることを検討する。

- 段階 4 に入れないもの: 実際の VPS・WireGuard・DNS・監視（段階 5）、20 万件の規模の試験（段階 6）、Box の作り、業者の実機の確認。

## 20. 計測の記録

### 20.1 N1: エッジの 1 テナントあたりのメモリー（2026-10-20、検証機）

道具と詳しい結果は `verify/n1/`。起動したばかりの dockerd（`docker:29.8.2-dind`、Debian 13 のホスト）で、radsec-edge の agent と同じひな形のテナントのコンテナを 160 まで増やして測った。

| 項目 | userland-proxy オフ | userland-proxy オン |
|---|---|---|
| 1 テナントあたり（AP 5 つ、接続なし） | 約 11.1 MiB | 約 15.0 MiB |
| 内訳（PSS） | containerd-shim 約 6.8、radsecproxy 約 2.0、カーネル（ネットワークの名前空間など）約 1.3、dockerd と containerd の増分 約 0.6 | 左に docker-proxy 約 3.6 が加わる |
| AP の接続 1 本あたり | 約 0.16〜0.2 MiB | 同じ |
| AP の設定（client ブロック）1 つあたり | 約 0.03 MiB | 同じ |
| Docker の土台（dockerd と containerd。イメージの読み込みの後） | 約 140 MiB | 同じ |

- 160 テナント・800 接続でも、すべての接続が受け付けられた。エッジの側の合計は、オフで約 2.1 GiB、オンで約 2.7 GiB。
- 以前に検証機のホストで見た dockerd の 450〜520 MB は、それまでの使われ方で膨らんだもので、起動したばかりの dockerd は約 80 MiB だった。検証機の dockerd（13 日動き続け、コンテナとイメージは 0）は RSS 480 MiB で、そのうち 403 MiB が Go のヒープ（anon）だった。その間に Go のイメージを何度も並べてビルドしており、dockerd の中で動く BuildKit で膨らんだヒープが残ったものと推測する。エッジではビルドしない（決定事項 24）が、整合ループ・ログの読み出し・healthcheck で dockerd を休みなく呼ぶので、長い時間の増え方は §16.4 で確かめる。
- 1 テナントあたりの大半は containerd-shim（コンテナごとに 1 つ）で、テナントごとにコンテナを分ける作りでは減らせない。docker-proxy の分は `userland-proxy: false` で消せる。

見積もり（仮定: ホスト OS と常駐の道具 300 MiB、エッジのプロセス 40 MiB、メモリーの 30% を余裕として残す、テナントあたり AP 5 つの接続）:

| エッジの VPS | userland-proxy オフ | userland-proxy オン |
|---|---|---|
| 2 GB | 約 70 テナント | 約 55 テナント |
| 4 GB | 約 185 テナント（計測のときのポートの範囲 170 が先に効いた。範囲は §9.1 で 2,000 に広げた） | 約 140 テナント |

### 20.2 R10: RadSec の受け口のラボ（2026-10-20、検証機）

道具と詳しい結果は `verify/r10/`。radsecproxy を 4 つ（Debian の 1.11.2、1.11.4 の無改造、PartialChain だけを足したもの、PartialChain と CRL の確認をリーフだけにする変更を足したもの）用意し、業者の CA の模型（Meraki の PureCA の 5 段、Mist の組織ごとの自己署名 CA）とこちらの CA の証明書で、52 の場面を確かめた。すべて期待どおり。

| 分かったこと | 場面 |
|---|---|
| 無改造の radsecproxy は自己署名でない CA を信頼の起点にできない。共通のルートを信頼すると、他の組織の Meraki の AP も通る | P2・P3 |
| PartialChain で RadSec 用の CA（または組織の CA）を起点にすると、自組織の AP だけを受け、他組織の AP を拒否できる。AP がリーフだけを送っても通る | P4〜P8 |
| パッチ版でも `PartialChain` を書かなければ無改造と同じ | P9 |
| 無改造で共通のルートを起点にすると、チェーンが 1 段深くなっただけで深さの上限で拒否される。PartialChain なら影響しない | P10・P11 |
| PartialChain だけでは、CRLCheck on と組み合わせると正当な AP も拒否される（起点の CA 自身の CRL を求められる、またはその CRL の署名を確かめられない）。CRL の確認をリーフだけにすると、RadSec 用の CA の CRL 1 つで、失効も含めて正しく動く | C1a・C2a・C1〜C3b |
| 組織の CA を起点にすると、RadSec 用の CA の CRL も要る | C4・C4b |
| 無改造で共通のルートを起点にすると、5 段すべての CRL が要る | C5・C6 |
| CRL のない CA が束にあっても、拒否されるのはその CA の証明書だけ | C7・C7c |
| こちらの CA と Meraki の模型を同じ束に混ぜても、それぞれ正しく受け入れ・拒否される | C8〜C8d |
| 共通のブロックがなければ、登録していない証明書・ブロックを消した証明書は拒否される。同じ SAN の新旧の証明書は両方つながり、古い方を失効させて SIGHUP を送ると古い方だけ止まる | B1〜B3d |
| CRLCheck off で、共通のブロックを CN の形で絞ると、業者の AP とこちらの証明書を受け分けられる。ただし失効させたこちらの証明書も通るので、ブロックを消して止める | M1〜M5 |
| テナントの刻印（偽の刻印は消して付け直す。別の業者の VSA は残る）、NAS-Identifier の置き換え・そのまま・補う、Accounting への刻印が、1.11.4 のパッチ版でも Debian の 1.11.2 でも効く | V1〜V7 |

確かめていないもの: 実物の業者の証明書と CRL、`PolicyOID` との組み合わせ、Status-Server、IPv6、radsec-edge の設定の生成と agent を通した反映。


### 20.3 エッジのテナントのコンテナのログの読み方（2026-10-31、検証機）

道具と詳しい結果は `verify/edge-logs/`。`docker:29.9.2-dind`（`userland-proxy` オフ、`live-restore` オン）に 150 テナント（AP 5 台ずつ）を置き、接続 750 本でログを出した後のエッジの側の合計を比べた。

| 方式 | 合計 | json-file との差 |
|---|---|---|
| json-file のみ | 2108 MiB | — |
| fluentd のログドライバー（データ面のノードと同じ値） | 2811 MiB | +703 MiB |
| fluentd のログドライバー（待ち行列と受信バッファーを絞る） | 2195 MiB | +87 MiB |
| json-file を Fluent Bit が tail で読む | 2152 MiB | +44 MiB |

- 既定の値では、ドライバーの待ち行列（`fluentd-buffer-limit`）がコンテナごとに、Fluent Bit の forward の受信バッファーが接続ごとに大きく取られる。1 テナントあたりの増分は約 4.7 MiB で、決定事項 25 の見積もりでは 4 GB で約 135 テナントになり、保証値の 150 を割る。値を絞ると約 0.6 MiB で、約 175 テナントのまま。
- 絞った fluentd のドライバーを採る（radsec-edge の設計概要 §24.11 の EA14）。`docker logs` は dual logging のキャッシュで読め、`userland-proxy` オフの `localhost` にも届き、`dockerd` の再起動の後も行が届く。tail は root で全コンテナのログを読むマウントが要り、行からテナントも分からない。
- データ面と管理面のノードはコンテナが少ない（数個）ので、値を変えない。
