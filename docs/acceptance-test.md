# 受入試験の手順書

- 対象: 運用担当（顧客を収容するときに受入試験を行う人）と、立ち会うシステム管理者。
- 内容: 顧客の拠点で、顧客の AP（またはグループの製品）と実際の SIM を使い、RadSec の接続から長い時間の接続の維持までを確かめる手順と、記録のしかた。
- AP の設定のしかたは書かない。aka-ossbss の [AP の接続の手順書](https://github.com/oyaguma3/aka-ossbss/blob/main/docs/ap-connection-guide.md)（以下「AP の接続の手順書」）を顧客に渡す。
- 運用担当の画面の操作は、aka-ossbss の運用ガイド 14 章（RadSec の受け口）を見る。
- 要件: [要件と構成の概要](requirements-overview.md) §16.2（受入試験）、§9.5（製品ごとの収容の方式）。
- 状態: MVP セットの v1.0.0（タグ `mvpset-v1.0.0`。2026-11）の版。段階 6-4 の予行（2026-11-17〜18、UniFi U7 Lite・Android の端末・USB のモデムの端末）の結果で直した。AT-12 は予行で FAIL だったので、エッジの直し（段階 6-5）の後に同じ環境で一晩やり直して PASS にし（2026-11-18〜19）、その結果でもう一度直した。予行の記録は `verify/acceptance/`。

## 1. 目的と範囲

受入試験では、次を顧客と一緒に確かめ、結果を記録する（§16.2）。

- 顧客の AP が RadSec でエッジにつながり、実際の SIM で EAP-AKA と EAP-AKA' が通る。
- 状態を止めた SIM と、別のテナントの SIM は拒否される。
- Accounting が届き、セッションと利用の集計に出る。
- エッジが 1 台止まっても、AP が予備のサーバーへ切り替わる。
- 証明書を差し替えられる。
- 何もしないまま長い時間置いても、接続と認証し直しが続く。
- 製品ごとの条件（ポート、証明書、NAS-Identifier の実際の値、証明書の差し替えが効くか）を確かめる（§9.5）。

入れないもの:

- 性能と規模（段階 6 の規模の試験で確かめた）。
- 持ち込みの CA の業者ごとの確かめ（その製品を収容するときに、この手順に足す）。

## 2. 役割

| 役 | すること |
|---|---|
| 運用担当 | テナントの RadSec の設定、AP・グループの登録と反映、試験用 SIM の radius 側の登録、確かめと記録、顧客への説明 |
| システム管理者 | DNS の CNAME の登録、試験用 SIM の vecgen 側（鍵）の登録、付け替え先のテナントの用意 |
| 顧客 | 鍵と CSR を作る、AP の設定、端末の操作、説明の了承 |

## 3. 前もって決めること（試験の 1 週間前まで）

顧客から次を聞き、記録の様式（8 章）に書く。

| 項目 | 内容 |
|---|---|
| AP の製品と版 | AP の接続の手順書 2 章の条件を満たすか。特に、2083 番以外のポートを設定できるか |
| 登録のしかた | AP・グループ・持ち込みの CA のどれにするか（AP の接続の手順書 3 章、§9.5） |
| NAS-Identifier | グループや持ち込みの CA では、AP が送る値がそのまま使われる。AP ごとに違う値（AP の MAC アドレスなど）を送る設定にできるか。決まった文字列やサイトの名前では、ルールで AP を見分けられない |
| サーバーの欄 | AP にサーバーを名前（ホスト名）で書けるか、IP アドレスだけか。IP アドレスだけなら、各スロットの名前が指すエッジの公開の IPv4 アドレスを運用担当が伝える。このとき、①サーバー証明書には名前しか入っていないので、AP が名前を IP アドレスと照らし合わせる作りならつながらない（AT-01 で確かめる。UniFi は照らし合わせない）、②スロットを別のエッジに移す（aka-ossbss の運用ガイド 14 章）と、顧客が AP の設定を書き換える必要がある |
| 拠点の公開のアドレス | 固定か。固定なら送信元の範囲で絞れる。共有の IPv4（DS-Lite など）では、同じアドレスをほかの利用者も使うので、範囲で絞る意味が小さい |
| SSID と暗号化 | 試験に使う SSID の名前（WPA2-Enterprise か WPA3-Enterprise） |
| 端末 | 試験の端末の種類（Android、iPhone、ほか）。EAP-AKA と EAP-AKA' を選べるか |
| 日時と立ち会い | 当日 2〜2.5 時間と、翌朝の確かめ |

## 4. 準備（試験の前の日まで）

1. **テナントの RadSec**（運用担当）: RadSec を有効にし、primary と secondary を別のエッジに置く。反映済みになったことを確かめる。
2. **DNS**（システム管理者）: 画面の「DNS に登録するレコード」の CNAME を登録する。公開のリゾルバーで引けることを確かめる。
3. **証明書**（顧客 → 運用担当）:
   - 顧客が鍵と CSR を作る（AP の接続の手順書 4.1）。鍵は受け取らない。
   - 運用担当が CSR を登録して発行し、「反映する」を押す（AP の接続の手順書 4.2・4.3）。
   - 証明書とサーバーCA の PEM を顧客に渡す。サーバーCA の SHA-256 のフィンガープリントは、PEM とは別の経路（電話、別のメール）で伝え、顧客が照らし合わせる。
     ```bash
     openssl x509 -in server-ca.pem -noout -fingerprint -sha256
     ```
4. **試験用 SIM**: 運用担当の試験用 SIM を、顧客のテナントに登録する。
   - vecgen 側はシステム管理者が画面で鍵（Ki・OPc）を入れる。鍵はチャットやメールに書かない。
   - AMF は既定の `8000` のままにする。EAP-AKA' では分離ビット（0x8000）が要り、`0000` だと端末が断る。
   - radius 側は運用担当が登録する。取得先は aka-vecgen、ルールは NAS-Identifier `*`・試験の SSID・Session-Timeout 3600。
   - SIM の SQN がほかのサーバーで進んでいれば、最初の認証で再同期が 1 回起きる（正常）。
5. **付け替え先のテナント**（システム管理者）: 空のテナントを 1 つ用意する（AT-08 で使う。試験の後に消す）。

## 6. 確かめる項目

「見るところ」の画面は aka-ossbss。ログは運用担当が読む（aka-radius の運用ガイド 9 章の `event_id`。拒否の理由は 6.2）。AP がつながらないときは aka-ossbss の運用ガイド 14.7。

| ID | 確かめること | 操作 | 期待する結果 | 見るところ |
|---|---|---|---|---|
| AT-01 | RadSec でつながる | AP の設定の後、待つ | 配置が反映済み。AP が primary のエッジにつながる | テナントの RadSec の「ログ」（`tlsservernew … up`）、AP・グループの「最後の接続」 |
| AT-02 | EAP-AKA で通る | 端末で EAP-AKA を選んでつなぐ | つながる | aka-radius の `AUTH_SUCCESS`（テナントが顧客のテナント） |
| AT-03 | EAP-AKA' で通る | 端末で EAP-AKA' を選んでつなぐ | つながる | 同上 |
| AT-04 | 再同期 | （SIM の SQN が進んでいれば最初の認証で起きる） | `EAP_RESYNC_CHALLENGE` の後に `AUTH_SUCCESS` | aka-radius のログ |
| AT-05 | NAS-Identifier と Called-Station-Id の実際の値 | 値を記録し、ルールの NAS-Identifier を `*` から実際の値に変えてつなぐ → 合わない値に変えてつなぐ。終わったら戻す | 実際の値なら通り、合わない値なら拒否される。値の形（大文字・小文字、区切りの文字）も記録する | `AUTH_SUCCESS` の `nas_identifier`。合わないときは `AUTH_POLICY_DENIED` の `nas_identifier`・`ssid`（Called-Station-Id の「:」の後ろ） |
| AT-06 | Accounting | つないだまま 10 分以上置き、切る | セッションの一覧に出て、更新の時刻が進む。翌日の利用の集計に出る | 「セッション」の画面、課金の画面の利用（翌日 3 時の取り込みの後） |
| AT-07 | 状態による拒否 | 試験用 SIM の radius 側を止めてつなぐ → 戻す | 止めている間は拒否、戻すと通る | `AUTH_SUBSCRIBER_INACTIVE` |
| AT-08 | 別のテナントの拒否 | 試験用 SIM の所属を付け替え先のテナントにしてつなぐ → 戻す | 付け替えている間は拒否、戻すと通る | `AUTH_POLICY_DENIED`（刻印のテナントとルールのテナントが合わない） |
| AT-09 | 送信元の範囲 | 拠点の公開のアドレスを範囲に入れてつなぐ → 範囲の外（例 `192.0.2.0/24`）にしてつなぐ → 顧客の希望の値に戻す | 範囲の中なら通る、外なら TLS に応じずつながらない | エッジのログの `ignoring unknown TLS client` |
| AT-10 | 予備のサーバーへの切り替え | primary のエッジのテナントのポートを止める（運用担当。10 章） | AP が secondary に切り替わって通る。戻したときに primary へ戻るかを記録する（製品による。戻らない製品もある） | 両方のエッジの「ログ」、切り替わるまでの時間 |
| AT-11 | 証明書の差し替え | 顧客が新しい鍵と CSR を作る → AP の詳細の「証明書の更新」で発行し「反映する」を押す（宣言の版が上がる） → 顧客が AP に入れ替える（AP の再起動が要る製品がある。11 章） → 古い証明書を「入れ替えた後の失効」→ エッジのコンテナを「再起動」して張り直させる | 張り直した後も通る（新しい証明書を使っている） | AP の詳細の証明書の一覧、エッジのログ |
| AT-12 | 長い時間の接続の維持 | 端末をつないだまま一晩置く | AP のエッジへの接続が閉じられずに続き、AP から届いた認証（Session-Timeout ごとの認証し直しを含む）がすぐ通り続ける。Accounting の Interim が届き続ける。端末がつながらない時間と認証し直しの遅れは、その間に AP から要求が来ていたかで切り分けて記録する | エッジのログの AP の接続（`tlsserverrd: timeout … (no requests), closing connection` が出ないこと、`tlsservernew … up` の時刻）、aka-radius のログの `PKT_RECV`（AP から要求が届いた時刻）と `AUTH_SUCCESS` の時刻の間隔、端末の接続の記録、セッションの一覧 |

- AT-07・AT-08 は、運用担当の試験用 SIM で行う。顧客の回線の SIM は止めない。
- AT-08 は、刻印（エッジが付けるテナント）で別のテナントの SIM を断ることを確かめる。付け替え先のテナントは空でよい。
- AT-09 は、拠点のアドレスが固定でない顧客では、範囲の外の確かめだけ行い、範囲は空に戻す。
- AT-10 は、データ面と管理面が止まる試験ではない。エッジが 1 台止まったときの AP の振る舞いだけを見る。
- AT-12 は、認証の成功の回数では判定しない。拒否が 0 でも、AP がエッジへの接続を張り直すのが遅れると認証し直しが遅れ、そのあいだ端末がつながらない（2026-11-17 の予行。エッジが要求のない AP の接続を 15 分で閉じていた。段階 6-5 で閉じないように直した）。端末ごとに `AUTH_SUCCESS` の時刻を並べ、Session-Timeout からの遅れを見る。
- 遅れやつながらない時間があったら、その間に aka-radius に AP からの要求（`PKT_RECV`）が来ていたかを見る。要求が来ていて通らなかった・遅れた、またはエッジが AP の接続を閉じていたなら、エッジと中央の側の問題として FAIL にする。要求が来ていない（端末が AP に切られてつなぎ直せない、端末がつなぎ直さない）なら、AP と端末の無線の側で起きたこととして記録し、顧客に伝える（判定はエッジと中央の側で行う。2026-11-18〜19 のやり直しで決めた）。

## 7. 顧客への説明（了承を記録する）

| 説明すること | 内容 |
|---|---|
| 単一障害点 | 認証の本体（データ面）と管理の画面（管理面）は 1 台ずつで、止まると認証ができない（エッジだけ 2 台以上） |
| IMSI が見える | 仮名による認証がないので、無線の区間で端末の IMSI（永続 ID）が見える |
| 反映と切り替えで接続が切れる | AP・グループの増減や送信元の範囲の変更の反映、エッジの切り替えのときに、AP の RadSec の接続がいったん切れる。端末がつなぎ直すことがある（証明書の更新と失効の反映では切れない） |
| 証明書の期限 | 証明書には期限がある。期限の前に更新し、入れ替えた後に古い証明書を失効させる |
| 送信元の範囲 | 拠点のアドレスが変わると、範囲の外になってつながらなくなる。変わるときは前もって連絡する |

## 9. 片付け

1. 試験用 SIM を顧客のテナントから消す（両側を止めて物理削除）。
2. 付け替え先のテナントを消す。
3. 試験用の SSID とルールの値を、顧客の運用の値に直す（ルールの NAS-Identifier、Session-Timeout）。
4. AT-11 で失効させた古い証明書が「失効」になっていることを確かめる。顧客は古い鍵を消す。
5. AT-10 で止めたポートが戻り、AP が primary につながっていることを確かめる。

## 10. 運用担当の操作

### 10.1 primary のエッジのテナントのポートを止める（AT-10）

primary のエッジで、テナントのポートだけを nftables の別の表で止める。消し忘れに備えて、15 分で自動で消える一時の timer をつける。

```bash
sudo systemd-run --quiet --unit=aka-at10-undo --on-active=900 /usr/sbin/nft delete table inet aka_at10
sudo nft add table inet aka_at10
sudo nft add chain inet aka_at10 pre '{ type filter hook prerouting priority -300 ; }'
sudo nft add rule inet aka_at10 pre tcp dport <テナントのポート> counter drop
```

戻すとき:

```bash
sudo nft delete table inet aka_at10 && sudo systemctl stop aka-at10-undo.timer
```

- ほかのテナントのポートは止めない（外形監視の probe のポートも止めない）。
- 止めている間も、画面の配置は「反映済み」のまま変わらない。

### 10.2 つながらないとき

| 症状 | 見ること |
|---|---|
| AP がつながらない（エッジのログに何も出ない） | DNS で名前が引けるか、ポートが合っているか、拠点から外向きの TCP が出られるか、送信元の範囲。サーバーを IP アドレスで書いた AP では、AP がサーバー証明書の名前の照合で断っていないか（AP のログ） |
| AP が TLS の途中で切る（エッジのログに `SSL accept from … failed: … unexpected eof while reading`） | AP がエッジのサーバー証明書を受け入れていない。CA・証明書・鍵を差し替えた直後なら、AP（製品によっては再起動）が新しいものを読み込んだか。サーバーCA を取り違えていないか |
| エッジのログに TLS の誤りが出る | 証明書と鍵が対か（下のコマンド）、サーバーCA を入れたか、証明書が失効していないか、反映済みか |
| `AUTH_SUBSCRIBER_NOT_FOUND`・`INACTIVE`・`TERMINATED` | 試験用 SIM の radius 側の登録と状態 |
| `AUTH_POLICY_DENIED` | ルールの NAS-Identifier と SSID（ログの `nas_identifier`・`ssid` と比べる）、所属のテナント |
| `AUTH_STAMP_*` | エッジの刻印の設定（aka-radius の運用ガイド 12 章） |
| EAP-AKA' だけ通らない | vecgen 側の AMF が `8000` か |
| 最初の認証だけ遅い・Session-Timeout の認証し直しが遅れる・端末がつながらない時間がある | まず、その間に aka-radius に AP からの要求（`PKT_RECV`）が来ていたか。来ていて通らない・遅いならエッジと中央の側を見る。来ていなければ、AP と端末の無線の側（端末が AP に切られてつなぎ直せない、端末がつなぎ直さない。11.1）か、AP が RadSec の接続を張り直すのを待っている（エッジのログの `tlsservernew … up` の時刻。段階 6-5 より前のエッジは要求のない接続を 15 分で閉じ、`tlsserverrd: timeout … (no requests), closing connection` が出た） |
| Accounting の `ACCT_SESSION_RESUMED`（INFO）が出る | 端末がキャッシュした鍵で EAP なしにつなぎ直した（Access-Accept がないので、aka-radius が Accounting の Start でセッションを作り直した）。利用は集計される |
| Accounting の `ACCT_SESSION_NOT_FOUND`（WARN）が出る | セッションがなく、作り直す材料（Class の値と IMSI）もない Accounting。AP が Class を返していないか、Stop だけが届いた。利用は集計される |

証明書と鍵が対かを確かめる:

```bash
[ "$(openssl x509 -in cert.pem -noout -pubkey | sha256sum)" = "$(openssl pkey -in key.pem -pubout | sha256sum)" ] && echo 対
```

### 11.1 Ubiquiti UniFi

- **サーバーの欄**: RADIUS のサーバーは IPv4 アドレスでしか書けない（ホスト名と IPv6 アドレスは書けない）。スロットの名前が指すエッジの IPv4 アドレスを書く。認証と Accounting のサーバーは同じ値（2 つ、テナントのポート、シークレット `radsec`）。
- **サーバー証明書の名前**: IP アドレスと照らし合わせない。名前だけのサーバー証明書でつながる。
- **PEM**: クライアント証明書・秘密鍵・CA 証明書の 3 つ（RADIUS のプロファイルに 1 組）。P-256 の鍵（PKCS#8）と P-256 の CA でつながる。
- **差し替え**: CA・クライアント証明書・秘密鍵を差し替えても、**AP を再起動するまで新しいものを読み込まない**。再起動しないと、エッジのログに `unexpected eof while reading` が出て、AP が TLS の途中で切り続ける。サーバーの欄とポート、NAS-Identifier の変更は「変更を適用」ですぐ効く。
- **NAS-Identifier**: 「AP MAC」「サイト名」「AP 名」「BSS ID」「カスタム」から選ぶ。「AP MAC」を勧める（AP ごとに違い、AP の名前を変えても変わらない）。値は小文字・コロン区切り（例 `74:f9:2c:…`）。Called-Station-Id は電波の MAC アドレス（BSSID。大文字・ハイフン区切りで、末尾が AP の MAC と違う）と SSID を「:」でつないだもの。ルールで AP を指すときは NAS-Identifier の形で書く。
- **切り替え**: primary が止まると数秒で secondary に切り替わる。primary が戻っても、secondary で動いている間は primary に戻らない（エッジの作業の後は、UniFi の AP が secondary に寄ったままになる）。
- **接続の維持**: 認証の接続では生存確認（Status-Server）を送らない。直す前のエッジは要求のない接続を 15 分で閉じ、次の認証のときの張り直しが 16〜59 分遅れることがあった（2026-11-17）。遅れている間は認証し直しが通らず、端末がつながらない。段階 6-5 でエッジが AP の接続を閉じないように直した後は、AP の 2 本の接続（認証と Accounting）が一晩（約 7 時間 35 分）張ったままで、認証し直しは Session-Timeout から 5〜22 秒で通った（2026-11-18〜19）。Accounting の接続は途中経過（600 秒ごと）で使われ続ける。
- **キャッシュでのつなぎ直し**: キャッシュした鍵（PMKSA）で EAP なしにつなぎ直す端末（Linux の wpa_supplicant など）では、Access-Accept がないので、aka-radius はその後の Accounting の Start でセッションを作り直す（`ACCT_SESSION_RESUMED`。段階 6-5 より前は `ACCT_SESSION_NOT_FOUND`。10.2）。キャッシュでつなぎ直した後は、Session-Timeout を過ぎても認証し直しが来ないことがあった（つなぎ直してから 64 分）。加入者を止めても、その端末は次に EAP で認証するまでつながり続ける。Android の端末は Session-Timeout ごとに EAP で認証し直した。
- **無線の側の切断**: Intel の無線の端末（Linux の wpa_supplicant）は、AP に関連付けた直後に AP から切られる（reason 7）ことがあり、続くと 2 分半〜12 分つながらなかった（一晩に 4 回）。Android の端末も、Session-Timeout で切られた後に 1 回だけ 16 分つなぎ直さなかった。どちらも、その間 AP は RADIUS の要求を送っていない（エッジと中央には届いていない）。原因は分かっていない。
- **Accounting の通信量**: Session-Timeout で切ったときの Accounting-Stop で、通信量が 0 で届くことがあった（一晩に 2 回）。直前の途中経過より小さいので aka-radius は WARN `USAGE_COUNTER_RESET` を出し、増えた分を 0 と数える。最後の途中経過から Stop までの通信量（最大で途中経過の間隔の 10 分ぶん）は数えられない。
