# 課金の締めを、本番から切り離した写しで測る（2026-11-17 08:42〜08:47、管理面の VPS）

締めは「今の月より前の月」だけを選ぶので、11 月の規模のデータは 12-01 まで締められない（試し用の口は製品に入れない）。
そこで本番の DB の写しを本番から切り離した一時の環境に戻し、事実・利用・RadSec の行を 1 か月前にずらして 2026-10 として締めた。
台本は ../charging-copy.sh。12-01 6:00 の本番の締めは、そのまま確かめとして残す。

## 一時の環境

- 写し: 3:00 の取り込みの後の本番の DB を pg_dump（13.0 MB、1.9 秒）→ 一時の postgres:18.6 に pg_restore（6.2 秒。DB 304 MB）。
- ずらした行（1 か月前へ）: 事実 411,325、利用の集計 141,746、AP 1,743（段階 5 の削除済みを含む）、配置 190、持ち込みの CA 0。10 月は全部の日を取り込んだ扱い。
- 一時の aka-ossbss: 本番と同じイメージ、開発用の設定（ループバックで待ち受け、システム管理者として動く）、一時の KEK、aka-provisioner に届かない宛先と
  ダミーの証明書、--internal のネットワーク（本番のコンテナにも外にも届かない）。ログは Fluent Bit に送らない（本番のアプリの数に入らない）。
- 試験用の PGP 鍵（ed25519 の署名鍵と cv25519 の暗号化の副鍵、期限 1 年。秘密鍵は手元だけ）を POST /charging/key で登録（種類 Curve25519）→ POST /charging/close。

## 結果

- 締め（scheduled_runs の 1 回）: 40.6 秒。利用の読み直しは届かずにすぐ失敗（取り込み済みの利用で締める）、計算と書き込みが約 29.3 秒、
  ファイルを作って保存が約 11.3 秒。
- 2026-10 を通し番号 1 で締めた: 回線 210,004、テナント 1,150、事実 411,325、訂正 0、取り込めなかった日 0。DB は 304 → 456 MB。
- ファイル charging_202610_000001_v1.zip.pgp は 4,310,383 バイト。平文の CSV は events 50.3 MB・lines 27.7 MB・tenants 0.1 MB。
- 中身: lines の registered_days の合計 3,560,033、認証の成功の合計 261,656（利用の集計の合計と一致）、利用のある回線 141,714、usage_complete はすべて true。
  tenants の lines_end の合計 210,001、aps_end 1,001、placements_end 40、削除済み 149（段階 5 の 148 テナントと s5a）。
  sc0001 は回線 20,000・AP 100・配置 2、sc0020 は vecgen 側だけの 10,000（radius_active_lines_end 0）、空のテナントは回線 0 で existed_days 17。
- 確かめ: 手元で verify/charging/verify-file.py（gpg・unzip・sha256sum）が「すべて合っています」（名前と manifest、完全性の検査、圧縮なし、件数と SHA-256、
  CSV の形、record_id）。平文は確かめた後に消した。

## 本番への影響と片付け

- 外形監視は失敗せず（最大 0.072 秒）、警告 0。本番の DB は鍵 0・締め 0 のまま（一時の環境の操作が届いていない）。
- 一時のコンテナ・ボリューム・ネットワーク・写し・KEK と台本は消した。

## 本番の鍵

同じ試験用の公開鍵を、本番の画面（/charging の「鍵を登録する」）から登録した（11-17 09:08。監査ログ charging.key）。
12-01 6:00 の本番の締めのファイルはこの鍵で暗号化されるので、手元の秘密鍵で開いて verify-file.py で確かめる。
鍵がないと 11-25 に CHARGING_KEY_WARN が出るが、登録したので出ない見込み。顧客を収容する前の作り直しで、受け取る側の鍵に入れ替える。
