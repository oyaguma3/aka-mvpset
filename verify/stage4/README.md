# 段階 4 の検証機の通し（エッジ 2 台、radsec-ca、実物の DNS、Cloudflare）

段階 4（エッジと CA）の終わりに、検証機 2 台で全ノードを組み合わせ、AP の役からの認証、証明書、反映、障害、移動、課金、画面、記録を確かめた道具と結果です。要件と構成の概要 §18.9 の S4-9 によります。

## 作り

```
ブラウザー（手元の playwright-cli）─Cloudflare Access─Tunnel─> cloudflared ─> aka-ossbss ── PostgreSQL
                                                                                  │ mTLS（共有ネットワーク）
                                                                                  ▼
                 ┌──────────────── mTLS（Tailscale）─────────────────── aka-provisioner ── aka-vecgen・aka-radius・radsec-ca
                 ▼                                                                                  │
   1 台目: edge-01（dind）──RADIUS・CRL の取得──────────────────────> aka-radius（auth・acct）・radsec-ca の配布の口
   2 台目: edge-02（dind）──RADIUS・CRL の取得（Tailscale）──────────┘
                 ▲
   2 台目: AP の役（radsecproxy。名前を実物の DNS で引き、証明書の名前も照合）<─UDP─ eapaka_test・radclient
```

- 中央・データ面・`edge-01` を 1 台目、`edge-02` と AP の役を 2 台目に置きます。2 台の間は Tailscale です。WireGuard は段階 5 です。
- エッジは `docker:dind` の中で運用ガイドのとおりに導入し、`userland-proxy` オフと `live-restore` オンを dind の dockerd に渡します（ホストの Docker の設定は変えません）。
- テナントは 3 つです。`alpha`（AP とグループ）、`bravo`（持ち込みの CA の Meraki 形の模型）、`charlie`（持ち込みの CA の Mist 形の模型と、こちらが発行した AP）。**業者の CA と Dashboard API は模型で、実物ではありません。**
- 製品に試し用の口は足していません。ずれはエッジの管理API を直接呼んで作り、課金の月と証明書の期限は試しの DB を SQL で動かします。偽の Dashboard API へは環境変数で向けます（`compose.ca.yaml`）。

| `drive.sh` | 手元の台本。段（下の表）ごとに検証機と画面を動かす |

## この環境だけのこと

- **aka-radius とエッジの radsecproxy から、別の機械の実際のアドレスが見えません。** Tailscale が `tailscale0` から転送するパケットに印を付けて MASQUERADE し（`ts-postrouting`）、dind は Docker が MASQUERADE するためです。ホストの設定は変えていません。
  - RADIUS クライアントは、aka-radius のネットワークのゲートウェイ（`auth` と `acct` で別の値）を 2 件登録し、エッジの上流のシークレットを 1 つにしました。本番ではエッジごとのトンネルのアドレスで登録します。
  - 送信元の範囲は、別の機械からは範囲の外になることに加えて、dind と同じ Docker のネットワークの AP の役（範囲の内と外の 2 つ）で判定しました。**エッジの Docker の公開を通っても送信元が保たれることは確かめましたが、WireGuard とインターネット越しに実際のアドレスが見えることは段階 5 で確かめます。**
- radsecproxy は名前を起動のときに引きます。AP の役は DNS を書き換えた後に作り直しました。実物の AP がいつ引き直すかは未確認です。
- エッジが 2 台だけで同じエッジに同じテナントを 2 つ置けないので、移動の前に `alpha` の `secondary` を外しました。移動の後の `alpha` の配置は 1 つです。

## 試して分かったこと

- 台本の誤りを直してやり直した項目があります。製品の不具合ではありませんでした。
  - `acct` は `auth` と別のネットワークにいるので、送信元が別のゲートウェイになります（`RADIUS_NO_SECRET`）。登録すると `no status server response` のログも止まります。
  - 範囲の外のテナントは 403 ではなく 404 です（画面仕様 §1 のとおり）。
  - エッジの `GET /tenants/{id}` には CA の本体がなく、AP の項目も宣言と違うので、そのまま `PUT` できません。
  - データを失ったエッジは DB の状態が次の周回まで前のままなので、番号が変わるまで待ちます。`server-cert` は標準エラーにもフィンガープリントを出すので、`2>&1` と混ぜて登録簿に書かないようにします（書くと 503 が続きます）。
  - 日をまたぐと、Accounting の集計は取り込める日になります。今日のキーを昨日に移す試しの手順は、同じ日のときだけ使います（昨日のキーを上書きするため）。
- Cloudflare 越しのフォームは、`page.context().request` で送るとブラウザーの Cookie を使えます（Origin のない要求なので CSRF の守りを通る）。

## 見つけたこと（確認事項）

製品の動きに不具合はありませんでした。文言と文書について、次の 3 点を確認事項として出し、合意して直しました（aka-ossbss の画面の文と運用ガイド、radsec-edge の運用ガイド。文言と文書だけなので、通しはやり直していません）。

1. 持ち込みの CA の画面の「CRL を取り直す」は radsec-ca までで、エッジは定期の取得（既定 5 分）で読みます。アップロードの画面には「エッジは次の取得で読みます」と出ますが、取り直しの文にはありません。
2. データを失ったエッジは管理API のサーバー証明書も新しくなるので、登録簿の `serverFingerprint` を改めるまで中継が 503 になります。radsec-edge の運用ガイド 10.8 に登録簿を書き換えることはありましたが、503 になる間の説明と、aka-ossbss の側の手順がありませんでした。
3. 同じエッジに同じテナントを 2 つ置けないので、2 台の構成で `primary` を移すには先に `secondary` を外します（その間は冗長がなくなります）。運用ガイド 14.9 に書いてありません。
